
# PROMPT MAÎTRE — REFONTE COMPLÈTE « UTILISATEURS & ACCÈS »
## INJS-LMD 2026 — Administration des comptes, rôles, permissions et habilitations
============================================================
0. MISSION
============================================================
Refondre complètement le module « Utilisateurs & Accès » de
l'application INJS-LMD 2026 afin d'en faire le centre de gouvernance
des identités, comptes utilisateurs, rôles, permissions et habilitations
de l'application.
OBJECTIF PRINCIPAL :
Permettre à l'administration INJS de :
1. gérer efficacement les comptes utilisateurs ;
2. créer, modifier, activer, suspendre et désactiver les comptes ;
3. attribuer les rôles de manière contrôlée ;
4. gérer les permissions ;
5. comprendre précisément ce que chaque rôle/permission autorise ;
6. connaître l'impact d'une habilitation sur les différents modules ;
7. éviter les privilèges excessifs ;
8. contrôler les accès sensibles ;
9. tracer toutes les opérations d'administration ;
10. contrôler périodiquement les habilitations ;
11. gérer les délégations lorsque le métier les autorise ;
12. disposer d'une vision claire des accès effectifs d'un utilisateur ;
13. empêcher qu'une modification d'accès produise un effet métier
    inattendu ou invisible.
La refonte doit être STRUCTURELLE, fonctionnelle, UX/UI, backend,
frontend, API, sécurité, audit et tests.
NE PAS se limiter à une modification esthétique.

4. ADMINISTRATION DES COMPTES
============================================================
Refondre la gestion des comptes.
Un administrateur doit pouvoir :
- rechercher un utilisateur ;
- filtrer ;
- consulter sa fiche ;
- créer un compte ;
- modifier les informations autorisées ;
- activer ;
- suspendre ;
- désactiver ;
- réactiver selon les règles ;
- forcer certaines opérations de sécurité si prévues ;
- attribuer/retirer un rôle ;
- consulter les permissions héritées ;
- consulter les permissions directes ;
- consulter les accès effectifs ;
- consulter l'historique des changements ;
- consulter les dernières activités pertinentes ;
- voir le statut du compte ;
- voir son périmètre organisationnel ;
- voir les modules accessibles ;
- voir les fonctions sensibles accessibles.
La fiche utilisateur doit répondre immédiatement à :
« Que peut faire exactement cet utilisateur dans l'application ? »
============================================================
5. FICHE UTILISATEUR — VUE DES ACCÈS EFFECTIFS
============================================================
Créer une vue claire des habilitations effectives.
Pour chaque utilisateur, distinguer :
- permissions issues des rôles ;
- permissions directes, si le système les autorise ;
- permissions héritées ;
- permissions temporairement déléguées ;
- permissions refusées ;
- permissions expirées ;
- accès résultant du périmètre organisationnel.
Afficher notamment :
UTILISATEUR
→ RÔLES
→ PERMISSIONS
→ MODULES
→ FONCTIONNALITÉS
→ ACTIONS AUTORISÉES
Exemple :
Utilisateur
  └── INJS_ADMIN
       ├── Utilisateurs & Accès
       │    ├── consulter
       │    ├── créer
       │    ├── modifier
       │    └── administrer
       ├── Scolarité
       │    ├── consulter
       │    └── administrer
       ├── Évaluations
       │    ├── consulter
       │    ├── saisir
       │    └── contrôler
       └── Présences
            ├── consulter
            └── administrer
Le système doit permettre de distinguer clairement :
« rôle attribué »
de
« droit effectivement utilisable ».
============================================================
6. GESTION DES RÔLES
============================================================
Refondre le référentiel des rôles.
Pour chaque rôle afficher :
- code ;
- libellé ;
- description ;
- domaine ;
- niveau de sensibilité ;
- statut ;
- disponibilité ;
- nombre de permissions ;
- nombre d'utilisateurs ;
- modules impactés ;
- fonctionnalités sensibles ;
- date de création ;
- dernière modification ;
- origine ;
- état système/personnalisable si cette distinction existe.
Un rôle sensible doit être visuellement identifiable.
Prévoir une fiche détaillée du rôle.
La fiche doit répondre à :
« Si j'attribue ce rôle à quelqu'un, que pourra-t-il faire ? »
============================================================
7. RÔLES CANONIQUES INJS
============================================================
Respecter strictement la gouvernance INJS.
Les rôles canoniques INJS doivent être clairement identifiés,
notamment :
- INJS_ADMIN
- CHEF_INJS_ADMIN
Identifier également tous les autres rôles réellement présents dans
le dépôt.
IMPORTANT :
CPFAE_ADMIN ne doit PAS devenir un rôle canonique INJS-LMD.
S'il existe pour des raisons historiques/compatibilité :
- le conserver sans destruction ;
- le signaler comme historique/compatibilité ;
- ne pas l'utiliser comme rôle métier INJS ;
- ne pas introduire de logique Sygepcpfae/CPFAE dans les modules INJS.
Aucune contamination métier INJS-LMD ↔ Sygepcpfae/CPFAE.
============================================================
8. PERMISSIONS
============================================================
Refondre la gestion des permissions.
Une permission doit être compréhensible humainement.
Éviter une simple liste technique de chaînes.
Présenter idéalement :
MODULE
→ RESSOURCE
→ ACTION
→ PORTÉE
Exemple conceptuel :
Évaluations
  Ressource : Notes
  Actions :
    - consulter
    - saisir
    - modifier
    - contrôler
    - verrouiller
    - publier
Les noms exacts doivent être dérivés du code existant.
NE PAS inventer des permissions qui ne correspondent à aucune capacité
réelle du système.
============================================================
9. MATRICE DES PERMISSIONS
============================================================
Créer une véritable matrice permettant de comprendre :
ROLE × MODULE × ACTION
Exemple :
| Rôle | Module | Consulter | Créer | Modifier | Contrôler | Publier | Administrer |
|------|--------|-----------|-------|----------|-----------|---------|-------------|
Ajouter si pertinent :
- portée ;
- niveau de sensibilité ;
- permission héritée ;
- permission directe ;
- restriction organisationnelle.
La matrice doit être :
- filtrable ;
- recherchable ;
- lisible ;
- exploitable ;
- exportable si une capacité d'export existe ou est pertinente ;
- protégée contre les modifications accidentelles.
============================================================
10. IMPACT D'UNE PERMISSION
============================================================
C'est une exigence MAJEURE.
Lorsqu'un administrateur consulte une permission, il doit pouvoir
comprendre son impact.
Pour chaque permission, rechercher et afficher :
- module concerné ;
- fonctionnalités concernées ;
- routes API concernées ;
- écrans concernés ;
- actions concernées ;
- rôles qui l'utilisent ;
- utilisateurs qui l'héritent ;
- niveau de sensibilité ;
- conséquences potentielles.
Exemple :
Permission :
EVALUATIONS.NOTES.MODIFIER
Impact :
- module Évaluations ;
- Saisie des notes ;
- modification des notes ;
- contrôle des notes potentiellement impacté ;
- utilisateurs héritant de cette permission ;
- rôles concernés.
NE PAS afficher un impact inventé.
L'impact doit être dérivé du code et/ou d'un référentiel technique
auditable.
============================================================
11. IMPACT D'UN RÔLE
============================================================
Depuis un rôle, afficher :
Rôle
→ Permissions
→ Modules
→ Fonctionnalités
→ Utilisateurs
→ Actions sensibles
Permettre de répondre :
« Que se passe-t-il si je donne ce rôle à cet utilisateur ? »
Et :
« Que se passe-t-il si je retire ce rôle ? »
Si le système ne permet pas de simuler réellement le changement,
fournir au minimum une vue d'impact avant/après.
============================================================
12. IMPACT D'UN UTILISATEUR
============================================================
Depuis un utilisateur :
Utilisateur
→ rôles
→ permissions
→ modules accessibles
→ fonctionnalités accessibles
→ actions sensibles
→ périmètre organisationnel
→ délégations
→ exceptions
→ historique
Créer une notion d'« accès effectifs ».
Cette vue est prioritaire.
============================================================
13. PORTÉE ORGANISATIONNELLE
============================================================
Si le système dispose de structures organisationnelles, identifier
comment les droits sont limités par :
- direction ;
- département ;
- service ;
- établissement ;
- formation ;
- filière ;
- promotion ;
- groupe ;
- autre périmètre réellement présent.
Une permission ne doit pas nécessairement signifier :
« accès à toute l'application ».
Elle peut signifier :
« accès à cette fonction dans ce périmètre ».
Documenter et implémenter ce comportement uniquement s'il correspond
au modèle réel.
============================================================
14. DÉLÉGATIONS
============================================================
Auditer puis refondre les délégations.
Une délégation doit permettre de savoir :
- qui délègue ;
- à qui ;
- quoi ;
- pourquoi ;
- périmètre ;
- date de début ;
- date de fin ;
- état ;
- approbation ;
- révocation ;
- historique.
Les délégations temporaires doivent être automatiquement considérées
comme expirées à la date prévue.
Une délégation sensible doit nécessiter les contrôles appropriés.
============================================================
15. PROVISIONNEMENT
============================================================
Si le mécanisme existe, créer une file de provisionnement claire.
Afficher :
- demandeur ;
- bénéficiaire ;
- rôle demandé ;
- permissions résultantes ;
- justification ;
- approbateur ;
- date ;
- statut ;
- urgence ;
- expiration éventuelle.
États possibles à déterminer dans le code :
- en attente ;
- approuvé ;
- rejeté ;
- exécuté ;
- expiré ;
- annulé.
NE PAS inventer des états inexistants sans nécessité architecturale.
============================================================
16. OPÉRATIONS EN MASSE
============================================================
Permettre les opérations de masse uniquement lorsqu'elles sont
sécurisées.
Exemples :
- attribuer un rôle ;
- retirer un rôle ;
- activer ;
- suspendre ;
- désactiver ;
- révoquer une délégation.
OBLIGATOIRE :
Toute opération de masse sensible doit :
- afficher le nombre de comptes concernés ;
- afficher un résumé ;
- demander confirmation ;
- afficher l'impact ;
- produire une trace d'audit ;
- gérer les erreurs partielles ;
- ne jamais provoquer une modification silencieuse.
============================================================
17. REVUE DES HABILITATIONS
============================================================
Créer une fonction de revue périodique des accès.
Objectif :
identifier :
- comptes inactifs ;
- rôles excessifs ;
- permissions sensibles ;
- utilisateurs sans activité ;
- délégations expirées ;
- comptes avec trop de privilèges ;
- rôles attribués sans justification ;
- comptes orphelins ;
- anomalies.
Prévoir un tableau :
UTILISATEUR | RÔLES | PERMISSIONS SENSIBLES | DERNIÈRE ACTIVITÉ |
RISQUE | ACTION RECOMMANDÉE
La revue doit être exploitable par l'administration.
============================================================
18. JOURNAL D'AUDIT IMMUTABLE
============================================================
La capture de référence montre explicitement :
« Toute action sur les habilitations est tracée dans un journal
immuable et horodaté. »
Respecter ce principe.
Tracer au minimum :
- création de compte ;
- modification de compte ;
- activation ;
- suspension ;
- désactivation ;
- attribution de rôle ;
- retrait de rôle ;
- modification de permission ;
- délégation ;
- révocation ;
- approbation ;
- rejet ;
- opération de masse ;
- changement de périmètre ;
- changement sensible de configuration.
Chaque événement doit contenir si disponible :
- acteur ;
- cible ;
- action ;
- ancienne valeur ;
- nouvelle valeur ;
- date/heure ;
- résultat ;
- justification ;
- origine ;
- adresse/IP ou contexte technique si déjà prévu ;
- identifiant de corrélation.
IMPORTANT :
Le journal d'audit ne doit pas être présenté comme modifiable par
l'utilisateur.
============================================================
19. SÉCURITÉ DES ACTIONS SENSIBLES
============================================================
Identifier les actions critiques.
Exemples :
- attribuer un rôle administrateur ;
- retirer le dernier administrateur ;
- modifier une permission sensible ;
- désactiver un administrateur ;
- modifier le périmètre d'un utilisateur ;
- opération de masse ;
- délégation privilégiée.
Pour ces actions :
- confirmation explicite ;
- contrôle des droits de l'acteur ;
- audit ;
- avertissement ;
- éventuellement double validation si le système le permet.
Éviter toute possibilité d'auto-escalade de privilèges.
Un administrateur ne doit pas pouvoir contourner silencieusement les
règles de sécurité par le frontend.

Point particulièrement important

J’ai volontairement placé « Accès effectifs » et « Impact intermodules » au centre de la refonte. C’est ce qui manque généralement aux simples écrans RBAC : avoir une liste de rôles et de permissions ne suffit pas.

Le résultat recherché est plutôt :

Compte → Rôle → Permission → Module → Fonctionnalité → Action → Périmètre → Impact → Audit

Ainsi, avant d’attribuer INJS_ADMIN, par exemple, l’administrateur doit pouvoir comprendre exactement ce que cette attribution va ouvrir, et après l’attribution pouvoir constater les accès réellement effectifs.

La capture montre déjà une bonne base ergonomique avec Comptes / Rôles / Matrice des permissions / Délégations / Provisionnement / Opérations en masse / Revue des habilitations / Journal ; le prompt transforme cette base en une véritable architecture de gouvernance, sans supposer que ces fonctionnalités sont déjà correctement implémentées.
