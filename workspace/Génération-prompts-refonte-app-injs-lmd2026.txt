PARTIE A — MODE D'EMPLOI DE CE JEU DE PROMPTS

A.1 — PRINCIPE DIRECTEUR (non négociable)
--------------------------------------------------------------------------------
La refonte est une REFONTE D'ALIGNEMENT, pas une réécriture [S1 §0]. Le socle
backend (Django 5.1.4 + DRF, 20 apps, 133 modèles, 943 tests) est éprouvé : il
est CONSERVÉ, COMPLÉTÉ et RENFORCÉ. L'identité visuelle INJS est CONSERVÉE.
L'application reste FONCTIONNELLE, OPÉRATIONNELLE et PERFORMANTE à la fin de
CHAQUE prompt. Il n'existe aucun état intermédiaire « cassé ».

A.2 — GRANULARITÉ
--------------------------------------------------------------------------------
Un prompt = une unité de travail livrable en 1 à 3 séances de travail, bornée,
testable et réversible. Chaque prompt produit un commit distinct (ou une petite
série de commits cohérents), derrière un feature flag quand il touche un
comportement existant.

A.3 — BOUCLE D'EXÉCUTION STANDARD (à appliquer à CHAQUE prompt)
--------------------------------------------------------------------------------
  1. Coller la PARTIE B (règles maîtresses) en tête de session.
  2. Coller le prompt choisi.
  3. L'agent LIT d'abord (arborescence, git status, fichiers concernés) et
     RESTITUE sa compréhension avant d'écrire du code.
  4. L'agent propose un plan découpé ; validation humaine.
  5. Implémentation par petites étapes, tests à chaque étape.
  6. Vérification obligatoire :
       backend  : python manage.py makemigrations --check --dry-run
                  python manage.py migrate
                  python manage.py test   (suite complète, 100 % vert)
       frontend : npm ci && npm run lint && npm run build && npm run test
       mobile   : flutter pub get --enforce-lockfile && flutter analyze
  7. Rapport final structuré (voir PARTIE B, règle 19) + capture d'écran des
     nouveaux écrans pour les manuels.
  8. Humain valide, puis on passe au prompt suivant.

A.4 — RÈGLE DES 3 FEUX VERTS
--------------------------------------------------------------------------------
Aucun prompt n'est considéré comme terminé tant que les trois feux ne sont pas
verts : (1) suite de tests backend 100 % vert, (2) lint + build + tests frontend
verts, (3) analyse mobile verte. Si l'un des trois était déjà rouge AVANT le
prompt, le LOT 0 doit l'avoir traité ; sinon le prompt s'arrête et signale.

A.5 — CE QUE CE DOCUMENT N'EST PAS
--------------------------------------------------------------------------------
Ce n'est pas une spécification fonctionnelle : c'est le [S2] qui fait foi pour
le « quoi ». Ce document dit « comment le demander, dans quel ordre, avec quels
garde-fous, et comment vérifier ». En cas de contradiction entre un prompt et
le [S2], le [S2] gagne sur le fond et le prompt gagne sur la méthode.

A.6 — CONVENTIONS D'ÉCRITURE DES PROMPTS
--------------------------------------------------------------------------------
  [CONTEXTE]    ce que l'agent doit savoir avant d'agir
  [MISSION]     l'objectif en une phrase
  [CONSIGNES]   le travail à faire, numéroté
  [INTERDITS]   les actions explicitement prohibées
  [LIVRABLES]   les fichiers/écrans/endpoints attendus
  [DoD]         définition du terminé, cases à cocher
  [RAPPORT]     ce que l'agent doit restituer
Les chemins cités proviennent de [S1] et doivent être RE-VÉRIFIÉS par le
prompt P00-01 avant tout usage : un chemin peut avoir bougé depuis l'audit.

RÈGLES MAÎTRESSES — PROJET INJS-LMD 2026 (app-injs-lmd2026demo)

Tu travailles sur l'application INJS-LMD 2026 de l'INJS Marcory (Abidjan, CI).
L'application est EN SERVICE. Elle doit le rester en permanence.

1. RÈGLE PRIORITAIRE
NE JAMAIS modifier, supprimer, déplacer ou remplacer massivement du code sans
avoir d'abord inspecté le projet existant. Avant toute intervention :
  1. identifier le répertoire courant ;
  2. inspecter l'arborescence (backend/, frontend/, qr_badge_mobile/, docs/,
     scripts/, .github/workflows/) ;
  3. identifier les frameworks et leurs versions RÉELLES (Django 5.1.4,
     DRF 3.15.2, React 18.2, Vite 7, Flutter — lire les fichiers de config) ;
  4. lire les fichiers de configuration concernés ;
  5. vérifier Git (branche, statut, derniers commits) ;
  6. comprendre l'architecture déjà présente.

2. NE PAS DÉTRUIRE L'EXISTANT
Ne jamais :
  - supprimer une application Django existante sans justification écrite ;
  - supprimer, réordonner ou réécrire des migrations existantes ;
  - supprimer une base de données ;
  - réinitialiser Git ; exécuter git reset --hard ; exécuter git clean -fd ;
  - supprimer massivement des fichiers ;
  - remplacer l'application existante par une nouvelle application ;
  - écraser le frontend existant ;
  - modifier le logo ou l'identité visuelle sans demande explicite ;
  - réintroduire l'ancienne application SYGEP-CPFAE / QR Badge / MEMFPMA.

3. GIT
Avant une modification importante : git status ; git branch --show-current ;
git log -5 --oneline. Après modification : git diff ; git status.
Ne jamais committer automatiquement sauf demande explicite.

4. MODIFICATIONS PAR PETITES ÉTAPES
Une tâche est découpée en petites étapes. Pour chaque étape : analyser,
modifier le minimum nécessaire, tester, vérifier les erreurs, présenter le
résultat, attendre la validation si l'opération est importante.

5. BASE DE DONNÉES
Ne jamais supprimer ou recréer la base sans confirmation explicite. Ne jamais
supprimer des migrations existantes pour « résoudre » un problème. Avant une
migration : makemigrations puis INSPECTER le résultat, ensuite seulement
migrate. Toute migration doit être réversible (fournir la marche arrière).

6. DONNÉES
Ne jamais supprimer les données de démonstration existantes sans confirmation.
Les données de démonstration sont séparables du code. Les identifiants internes
Django/PostgreSQL ne sont jamais utilisés comme identifiants métier visibles.

7. API
Le frontend web (React) et mobile (Flutter) communiquent UNIQUEMENT avec
Django/DRF. Jamais d'accès direct à PostgreSQL depuis le frontend. Toutes les
permissions sont vérifiées côté backend : l'UI ne masque jamais, elle filtre.

8. SÉCURITÉ
Ne jamais placer mot de passe, SECRET_KEY, clé JWT, clé API, clé de paiement,
identifiant SMTP ou secret SMS dans Flutter, Git ou le code frontend. Variables
d'environnement ou gestion de secrets uniquement.

9. PERMISSIONS
Conserver le système de droits N0–N4 existant et les 12 rôles métier existants
(ADMIN, CHEF_CPFAE_ADMIN, CPFAE_ADMIN, DIRECTION, CHEF_SECRETARIAT, SECRETARIAT,
FINANCE, ARCHIVE, ENCADRANT, SUPERVISEUR, FORMATEUR, AUDITEUR). Ne pas
remplacer arbitrairement le système de permissions. Toute évolution doit être
rétrocompatible avec les rôles, permissions et périmètres existants.
La matrice UI (frontend/src/utils/roles.js) doit rester alignée sur
role_groups.py — et, à partir du prompt P00-06, dériver de l'endpoint de
capacités du backend.

10. IDENTIFIANTS MÉTIER
Les interfaces et exports affichent des codes et libellés métier
(MAT-2026-00125, EM-LIC, EM-L2, EM101, CAND-2026-000154), jamais
student_id=125 / formation_id=7 / module_id=43.

11. RÉFÉRENTIELS
Ne jamais coder en dur dans React ou Flutter les formations, modules, niveaux,
salles, types, catégories, grades, années ou autres référentiels. Ces données
proviennent de l'API.

12. NOTES
Une note validée ou publiée n'est JAMAIS modifiée silencieusement. Toute
correction passe par un objet de correction traçable (motif, auteur, date,
valeur avant, valeur après).

13. FINANCES
Une opération financière validée n'est JAMAIS supprimée physiquement.
Utiliser annulation, régularisation ou remboursement selon le workflow prévu.
Les deux domaines financiers (finances étudiantes / rémunération des
formateurs) restent STRICTEMENT séparés : modèles, écrans et droits distincts.

14. DOCUMENTS
Les documents validés/signés sont immuables. Utiliser la gestion de versions.

15. AUDIT
Les opérations sensibles sont journalisées : utilisateur, date, action, objet,
ancienne valeur, nouvelle valeur, justification, résultat.

16. AVANT TOUTE NOUVELLE FONCTIONNALITÉ
Répondre d'abord : où cette fonctionnalité existe-t-elle déjà ? Quel module
métier ? Quel modèle Django ? Quelle API existe déjà ? Quel écran existe déjà ?
Quel rôle est autorisé ? Quel workflow existe déjà ? NE PAS CRÉER DE DOUBLON.

17. PAS DE REFACTORING MASSIF
Si une fonctionnalité peut être ajoutée avec une modification locale,
privilégier cette solution. Ne pas refactoriser toute l'application pour
résoudre un problème local.

18. TESTS
Après toute modification : lancer les tests concernés ; vérifier les imports ;
vérifier les migrations ; vérifier l'API ; vérifier le frontend concerné ;
vérifier la console ; vérifier git diff.

19. RAPPORT FINAL
Après chaque tâche, fournir :
  - Modifications : liste précise des fichiers modifiés ;
  - Fonctionnalités : ce qui a été ajouté ou corrigé ;
  - Tests : tests effectués et résultats chiffrés ;
  - Risques : problèmes éventuels restant à traiter ;
  - Prochaine étape : UNE seule prochaine étape recommandée.

20. INTERDICTION DE DEVINER
Si une information fonctionnelle ou technique manque : NE PAS INVENTER.
Identifier l'information manquante et demander confirmation.

PARTIE C — DÉCISIONS D'ARCHITECTURE IMPOSÉES (DA-01 → DA-12)
================================================================================
Ces décisions tranchent les tensions entre le [S2] (architecture cible idéale)
et le [S1] (état réel du dépôt). Elles s'imposent à tous les prompts.

DA-01 — CONSERVATION DE L'ARBORESCENCE DJANGO EXISTANTE
Le [S2] propose une arborescence cible backend/apps/{core, identity, referentials,
students, academics, teachers, timetable, attendance, assessments, results,
graduation, campus, finance, accounting, hr, administration, documents,
notifications, reports, audit}. Le dépôt réel contient 20 apps métier à plat
(backend/<app>/). DÉCISION : on NE RENOMME PAS et on NE DÉPLACE PAS les apps
existantes (coût de migration, risque de casse des 184 migrations, des imports
et des tests). On CRÉE les apps manquantes en respectant la nomenclature du
dépôt (comptabilite, notifications, portails, core). La table de correspondance
de la PARTIE D devient la carte officielle. Le [S2] précise lui-même : « cette
structure est une cible. Cline doit d'abord inspecter l'arborescence réelle
avant de créer, déplacer ou supprimer quoi que ce soit. »

DA-02 — UNE SEULE SOURCE DE VÉRITÉ PAR OBJET
Aucun doublon de référentiel. Une Formation de référence unique utilisée par
admissions, scolarité, pédagogie, enseignants, EDT, notes, jurys, diplômes et
statistiques. Un Espace unique (et non une table Piscine, une table Gymnase…).
Un Groupe unique (scolarite.Groupe). Un Module/ECUE unique.

DA-03 — SOFT DELETE ET HISTORISATION
Aucune suppression physique sur les données académiques, financières et
documentaires. is_active / deleted_at + journal (ancienne/nouvelle valeur,
utilisateur, date, motif).

DA-04 — ANNÉE ACADÉMIQUE OBLIGATOIRE
Toute donnée académique temporelle est rattachée à une année académique.
Une seule année académique active à la fois (contrainte déjà testée, à
conserver). Une année clôturée ne permet plus de modifier les résultats
académiques définitifs.

DA-05 — RBAC = NIVEAU × RÔLE × PERMISSION × MODULE × PÉRIMÈTRE × ÉTAT
L'autorisation ne dépend jamais d'un simple nombre. Exemple : ENSEIGNANT + N2 +
NOTES.MODIFIER + SES GROUPES + NOTE NON VALIDÉE → autorisé ; ENSEIGNANT + N2 +
NOTES.MODIFIER + AUTRE FORMATION → refusé. Périmètres : INJS_ENTIER, DIRECTION,
SERVICE, FORMATION, PARCOURS, NIVEAU, GROUPE, MODULE, ETUDIANT, PROPRE_COMPTE.
Actions : CONSULTER, CRÉER, MODIFIER, SOUMETTRE, VALIDER, REJETER, PUBLIER,
ANNULER, EXPORTER, IMPRIMER, ARCHIVER, SUPPRIMER, ADMINISTRER.
Les 12 rôles existants sont CONSERVÉS et mappés sur N0–N4 ; les rôles
additionnels du [S2] (COMPTABILITE, DOCUMENTATION, PATRIMOINE, JURY, CANDIDAT,
CONSULTATION) sont AJOUTÉS, pas substitués.

DA-06 — FEATURE FLAGS POUR TOUT CHANGEMENT DE COMPORTEMENT
Tout changement d'un comportement existant est livré derrière un flag
(Parametre côté backend + variable d'environnement) activable par rôle et par
domaine, désactivable en une minute sans redéploiement du code.

DA-07 — DEUX FINANCES, JAMAIS FUSIONNÉES (D5)
finances_etudiantes (frais de scolarité LMD) et formations.Finance*
(rémunération horaire des formateurs) restent deux sous-systèmes autonomes,
avec leurs propres modèles, écrans, droits et exports. Le seul lien autorisé
est analytique (remontée vers le module 12 — Direction financière).

DA-08 — GABARIT D'ÉCRANS UNIQUE POUR LES DOMAINES ORPHELINS
Les 4 domaines sans UI (stages, patrimoine, RH, administrations) sont livrés
avec UN gabarit React réutilisable : liste filtrable + pagination serveur +
détail + timeline de statut + pièces jointes + exports. Objectif : homogénéiser
l'UX et diviser le coût de livraison [S1 §14, LOT 3].

DA-09 — CONTRAT EDT v1.1 CONSERVÉ
Le contrat de données en lecture seule /api/scolarite/edt/ vers le planificateur
externe (app-ept-injs-lmd 2026) est CONSERVÉ et VERSIONNÉ. Le moteur de
génération natif (LOT 6) est complémentaire, pas concurrent : il produit des
brouillons validables, l'ingestion externe produit des séances actives.

DA-10 — LE MODULE 16 (BI) EST EN LECTURE SEULE
Le module de rapports/statistiques/BI ne modifie jamais les données métier.
Il agrège. Les agrégats lourds passent par des tables de synthèse incrémentales
et le cache Redis, jamais par des requêtes lourdes en ligne.

DA-11 — LE MODULE 17 (PORTAILS) NE RECRÉE AUCUN MÉTIER
Les portails exposent les API existantes selon les droits. Aucun modèle métier
dans la couche portail. Un portail = navigation + tableaux de bord + accès aux
API filtrées.

DA-12 — LE RETRAIT DU LEGACY EST LE DERNIER GESTE
Le socle HTML legacy (dashboard/views_legacy.py, templates de badgeage,
backend/static/sw.js « qr-badge-v3 », CDN html5-qrcode / Bootstrap 5.3) n'est
retiré qu'APRÈS bascule vérifiée des fonctions correspondantes, derrière un
flag, avec une fenêtre d'observation. Retirer avant de basculer est interdit.

P06-02 — MOTEUR DE GÉNÉRATION AUTOMATIQUE AVEC EXPLICATION DES ÉCHECS
Lot 6 | 3 séances | Dépendances : P06-01 | Module réf. : 06 §16-19
Risques couverts : E4 | Type : Moteur — CRITIQUE

>>> PROMPT P06-02 ─────────────────────────────────────────────────────────────
CONTEXTE
Le modèle de référence décrit précisément le moteur attendu :
« 1. Charger les enseignements 2. les groupes 3. les enseignants 4. les espaces
5. les disponibilités 6. le calendrier 7. les contraintes 8. Générer les
possibilités 9. Éliminer les conflits 10. Optimiser 11. Générer une proposition
12. Contrôler 13. Soumettre à validation 14. Publier ».
Et surtout : « Le système ne doit jamais simplement afficher "Génération
impossible". Il doit expliquer : 3 séances non planifiées : TD Module X –
Groupe L2-A → Aucun espace disponible de capacité ≥ 45 → Aucun créneau
compatible entre 14h et 18h. »

MISSION
Livrer un moteur de génération native qui produit une proposition contrôlée,
optimisée et EXPLIQUÉE, sans jamais échouer silencieusement.

CONSIGNES
1. Implémente le moteur en 14 étapes distinctes et testables unitairement,
   conformément à la séquence de référence. Chaque étape est une fonction pure
   avec entrée/sortie typée.
2. Étape d'élimination des conflits : utilise le validateur unique
   verifie_contraintes (P06-01). Aucune contrainte dure violée dans la
   proposition.
3. Fonction d'objectif configurable :
   Score = w1·pénalité_conflits + w2·pénalité_trous_étudiants +
           w3·pénalité_trous_enseignants + w4·pénalité_espaces_inutilisés +
           w5·pénalité_déplacements + w6·pénalité_déséquilibre
   Les poids sont PARAMÉTRABLES (pas de constantes en dur) et versionnés avec
   la proposition.
4. EXPLICATION DES ÉCHECS — exigence non négociable : pour chaque séance non
   planifiée, le moteur produit un objet d'explication structuré : séance,
   groupe, contraintes bloquantes, créneaux testés, raisons précises
   (« aucun espace de capacité ≥ 45 », « enseignant indisponible », « tous les
   créneaux 14h-18h occupés »), et SUGGESTIONS d'action (libérer un espace,
   augmenter la capacité, déplacer l'indisponibilité, scinder le groupe).
   Ces explications sont affichées à l'utilisateur et exportables.
5. Performance : le moteur doit traiter un jeu réaliste INJS (150
   enseignements, 400 séances, 25 enseignants, 12 groupes, 35 espaces) en moins
   de 5 minutes. Exécute-le en tâche de fond (pas dans la requête HTTP) avec
   statut consultable (EN_ATTENTE, EN_COURS, TERMINE, ECHEC) et progression.
6. Reproductibilité : mêmes entrées + mêmes contraintes + même graine aléatoire
   → même proposition. La graine est stockée avec la proposition.
7. La proposition est créée en BROUILLON : rien n'est publié, rien n'affecte
   l'existant tant que la validation n'est pas faite (P06-03).
8. Tests : chaque étape, chaque contrainte dure (aucune violation possible),
   explication des échecs (structure et contenu), reproductibilité, borne de
   performance mesurée.

INTERDITS
- Ne publie jamais automatiquement une proposition.
- N'écrase jamais un EDT existant : une proposition est un objet distinct.

DoD

[ ] fonction d'objectif paramétrable et versionnée

INTERDITS

REC-14 · MODULE 14 — DOCUMENTS, COURRIERS & ARCHIVES
--------------------------------------------------------------------------------

CRITÈRES : numérotation séquentielle · parapheur paramétrable avec délégation ·

certificat · indexation GED sans déplacement des documents existants.

REC-15 · MODULE 15 — NOTIFICATIONS

REC-16 · MODULE 16 — RAPPORTS, STATISTIQUES & BI

CRITÈRES : indicateurs exacts · drill-down fonctionnel · bilans existants

REC-17 · MODULE 17 — PORTAILS
--------------------------------------------------------------------------------
Consulter le portail public sans authentification (formations, campagnes,
calendrier, vérification d'un document), créer un compte candidat, déposer un
dossier, le suivre. Consulter le portail étudiant (EDT, notes publiées,
finances, documents), le portail enseignant (EDT, QR de présence, saisie de
notes), le portail personnel (dossier RH, congés). Tester le mobile hors-ligne.
CRITÈRES : portail public sans donnée nominative et avec throttling · isolement
strict entre candidats et entre étudiants (tests croisés) · aucun modèle métier
dans la couche portail · cache hors-ligne avec indicateur de fraîcheur.

CRITÈRES : 2FA effective pour les rôles N4 · matrice exécutable et simulable ·
audit complet (qui, quand, quoi, avant/après) · flag désactivable en < 1 min ·
contrôles d'intégrité verts · restauration réussie avec smoke test vert.
