0.2 LES QUATRE CONSÉQUENCES OPÉRATIONNELLES
---------------------------------------------------------------------------
Ces contraintes ne sont pas des détails : elles changent la façon de travailler.

(a) AUCUN SERVEUR POSTGRESQL, AUCUN DOCKER.
    La suite de tests Django ne peut pas s'exécuter sur la base de production.
    Parade : un overlay de réglages bascule sur SQLite en mémoire pour les
    tests (généré par le bootstrap). LIMITES À CONNAÎTRE : si le projet active
    django.contrib.postgres, ou s'il emploie des recherches vectorielles, des
    opérateurs JSONB ou des expressions SQL propres à PostgreSQL, ces tests
    échoueront sur SQLite. L'overlay émet un avertissement explicite dans ce
    cas. Les pistes concernées (LOT 9 finances, LOT 11 BI) doivent être
    revalidées contre un PostgreSQL réel avant leur gate.

(b) FLUTTER ABSENT.
    Le troisième feu vert (flutter analyze) ne peut PAS être levé dans Arena.
    Le script ne le simule jamais : il affiche « NON LEVABLE ». La piste
    mobile est donc développée ici mais validée sur un poste équipé.
    Conséquence de pilotage : prévoir ce contrôle hors sandbox à chaque gate
    de vague, sinon on accumule de la dette invisible sur 20 semaines.

(c) PYTHON 3.13 AU LIEU DE 3.12.
    Certaines dépendances épinglées pour 3.12 peuvent refuser de s'installer
    ou changer de comportement. Le bootstrap installe d'abord le
    requirements.txt tel quel ; en cas d'échec il retente sans psycopg2 et
    journalise tout dans arena/.bootstrap.log. Tout écart de version doit
    être inscrit au registre des écarts (onglet « Écarts E »), pas corrigé
    en silence.

(d) LE SNAPSHOT NE CONSERVE PAS L'ENVIRONNEMENT D'EXÉCUTION.
    Les fichiers sous /home/user persistent entre les sessions. Les dossiers
    .venv, node_modules, dist, build, __pycache__ ne persistent PAS.
    Conséquence : le code survit, l'environnement non. D'où le bootstrap
    idempotent à relancer en début de chaque session (étape 1).
    Autre limite : le snapshot est plafonné autour de 128 Mo et 10 000
    fichiers. Ne jamais commiter node_modules ni les médias lourds.

C'est l'étape bloquante : sans code, aucun des 92 prompts ne peut être

Ne jamais écrire le nom accentué entre guillemets dans une commande. Faire :

    for f in *.zip; do mv "$f" /home/user/projet.zip; done

3. ÉTAPE 1 — BOOTSTRAP DE SESSION (à chaque ouverture de session)
================================================================================

    cd /home/user && bash arena/bootstrap.sh

Ce que fait le script, dans l'ordre :

  1. Localise les trois pistes (manage.py, package.json, pubspec.yaml).
  2. Compare l'interpréteur à la cible 3.12 et signale l'écart.
  3. Crée le venv s'il manque, met pip à jour, installe requirements.txt.
     En cas d'échec, retente sans psycopg2 et journalise.
  4. Installe les dépendances frontend (npm ci si package-lock.json existe,
     npm install sinon).
  5. Génère arena/settings_sandbox.py, overlay qui réimporte TOUS les
     réglages réels du projet puis ne remplace que PostgreSQL, le SMTP et
     le broker de tâches.
  6. Écrit .gitignore-arena.

Sortie attendue sur un projet sain :

  == 1. Localisation des pistes
    [ok] backend  : /home/user/<projet>/backend
    [ok] frontend : /home/user/<projet>/frontend
    [attention] mobile : pubspec.yaml introuvable (piste Flutter absente)
  == 2. Interpréteur Python
    [attention] Python 3.13 — le projet vise 3.12...
  == 3. Dépendances Python
    [ok] requirements installés
    Django 5.1.4 sur Python 3.13.14
  == 5. Réglages de sandbox (non invasifs)
    [ok] arena/settings_sandbox.py écrit (overlay de <module>.settings)
  PRÊT — Django (5, 1)

L'overlay a été testé : il conserve bien INSTALLED_APPS du projet
(vérifié : ['django.contrib.contenttypes', 'django.contrib.auth',
'rest_framework', 'demo']) tout en imposant SQLite, ALLOWED_HOSTS=['*'],
CSRF_TRUSTED_ORIGINS=['https://*.e2b.app'] et le backend courriel en mémoire.

DURÉE : 2 à 5 minutes la première fois, quelques secondes ensuite.

5. ÉTAPE 3 — LA BOUCLE UNITAIRE : UN PROMPT = UNE SESSION
================================================================================

C'est le cœur du dispositif. 92 fois, dans l'ordre du plan.

5.1 OUVRIR LE BON PROMPT
---------------------------------------------------------------------------
Consulter le plan, section 6 (déroulé des vagues) ou l'onglet « Gantt » du
classeur. Identifier le prompt du jour et VÉRIFIER SES PRÉREQUIS : annexe B
du plan donne les dépendances de chacun des 92 prompts. Un prompt dont un
prérequis n'est pas terminé ne s'ouvre pas.

5.2 LE MESSAGE À ENVOYER DANS ARENA
---------------------------------------------------------------------------
Une session, un prompt, rien d'autre. Composer le message ainsi :

    [1] Coller prompts/00-REGLES-MAITRESSES.txt          (les 22 règles)
    [2] Coller prompts/LOTnn_Pxx-yy.txt                  (le prompt du jour)
    [3] Ajouter le contexte de session, par exemple :

        « Le code est dans /home/user/<projet>. L'environnement vient
         d'être bootstrappé. Précédent prompt terminé : P0x-0y.
         Exécute ce prompt dans le respect des 22 règles maîtresses.
         Ne touche à aucun autre module. Termine par les 3 feux verts
         via bash arena/feux-verts.sh P0x-0y et présente-moi le diff. »

Pourquoi un seul prompt par session : la fenêtre de contexte d'une session
n'absorbe pas plusieurs lots, et mélanger deux prompts produit des
régressions croisées impossibles à attribuer.

5.3 CE QUE LA SESSION DOIT PRODUIRE
---------------------------------------------------------------------------
  · du code, sur la piste concernée uniquement ;
  · les migrations correspondantes, générées et nommées ;
  · des tests : un prompt sans test n'est pas terminé ;
  · le diff, présenté avant validation ;
  · aucune modification hors périmètre du prompt.

5.4 LES 3 FEUX VERTS
---------------------------------------------------------------------------
    bash arena/feux-verts.sh P0x-0y

  FEU 1 — BACKEND : makemigrations --check --dry-run · check · test
  FEU 2 — FRONTEND : lint · build · test
  FEU 3 — MOBILE : flutter analyze  →  NON LEVABLE dans Arena

Sortie réelle observée sur projet de test, cas passant :

    FEU 1 backend  : VERT
    FEU 2 frontend : VERT
    FEU 3 mobile   : NON LEVABLE
    contrôles verts : 6   rouges : 0   non levables : 1
    VERDICT : GATE PASSÉE pour ce qui est vérifiable dans Arena.
    [code de retour 0]

Cas refusant, réellement observé :

    [KO] tests Vitest — voir arena/feux-verts.log
    FEU 2 frontend : ROUGE
    VERDICT : GATE NON PASSÉE — corriger avant d'ouvrir le prompt suivant.
    [code de retour 1]

Règle absolue : code de retour 1 = le prompt n'est PAS terminé. On corrige
dans la même session. On n'ouvre jamais le prompt suivant sur un rouge.

Exception documentée : avant P00-04 (filet de sécurité Vitest), le feu 2
« test » est rouge faute de tests existants. C'est attendu, et le script le
dit. Ce n'est pas une dérogation silencieuse.

5.5 COMMIT ET TRAÇABILITÉ
---------------------------------------------------------------------------
    cd /home/user/<projet>
    git add -A
    git status                      # vérifier : ni .venv, ni node_modules
    git commit -m "P0x-0y — <titre du prompt> [LOT n]"

Un commit par prompt. Le message porte l'identifiant du prompt : c'est ce
qui permet de rejouer le rollback niveau 2 (revert du commit) décrit dans
la partie G du livrable.

Puis mettre à jour le classeur, onglet « Prompts » : statut, date, commit,
et le jalon éventuellement atteint.

6. ÉTAPE 4 — LES GATES DE VAGUE
================================================================================

Dix gates, G1 à G10, une par vague. Une gate ne se franchit pas au
pourcentage d'avancement : elle se franchit sur des preuves.

À CHAQUE GATE
---------------------------------------------------------------------------
  1. Tous les prompts de la vague sont au statut « terminé » dans le classeur.
  2. bash arena/feux-verts.sh G<n> — vert sur les feux levables.
  3. bash arena/probe.sh — comparaison avec la baseline : aucune régression
     non expliquée. Une hausse du nombre de print() ou une baisse du nombre
     de tests est une régression.
  4. Les scénarios de recette de la vague (onglet « Recette », REC-01→REC-18)
     sont joués et cochés.
  5. Le feu 3 (Flutter) est validé hors sandbox — sinon la gate est
     « passée sous réserve » et la réserve est inscrite au classeur.
  6. Les risques R concernés sont re-cotés.
  7. Le pilote signe. Sans signature, la vague suivante ne démarre pas.

CE QUI BLOQUE UNE GATE
---------------------------------------------------------------------------
  · un feu rouge non traité ;
  · une migration manquante (makemigrations --check non vide) ;
  · un test désactivé pour passer ;
  · une régression de la baseline non arbitrée ;
  · une décision d'architecture (DA-01→DA-12) contredite par le code livré.

8. LES SERVEURS DE DÉVELOPPEMENT SOUS ARENA
================================================================================

Pour voir l'application tourner, deux règles impératives.

RÈGLE 1 — UTILISER UN PROCESSUS D'ARRIÈRE-PLAN, PAS UNE COMMANDE
---------------------------------------------------------------------------
Une commande shell est tuée à la fin de son exécution : un serveur lancé
ainsi meurt aussitôt. Les serveurs se lancent en processus d'arrière-plan
persistant (start_process). Ne JAMAIS lancer `npm run dev` ou `runserver`
via une commande simple.

RÈGLE 2 — ÉCOUTER SUR 0.0.0.0 ET AUTORISER L'HÔTE DE PRÉVISUALISATION
---------------------------------------------------------------------------
La prévisualisation est servie sur un hôte dynamique de la forme
https://{port}-{sandboxId}.e2b.app. Un serveur lié à 127.0.0.1 est
invisible ; un serveur qui refuse cet hôte renvoie une erreur.

  Backend Django — l'overlay le fait déjà (ALLOWED_HOSTS = ["*"],
  CSRF_TRUSTED_ORIGINS = ["https://*.e2b.app"]). Lancement :

      python manage.py runserver 0.0.0.0:8000 --settings=arena.settings_sandbox

  Frontend Vite — ajouter dans vite.config.js :

      server: {
        host: true,          // écoute sur 0.0.0.0
        port: 5173,
        allowedHosts: ['.e2b.app'],
        proxy: { '/api': 'http://localhost:8000' }   // proxy côté serveur
      }

  Point essentiel : le navigateur de l'utilisateur N'EST PAS le sandbox.
  Le code côté navigateur ne doit jamais appeler localhost ou 127.0.0.1
  pour joindre l'API. Utiliser des chemins relatifs (/api/...) et laisser
  le serveur de dev proxyfier vers le backend.

RÈGLE 3 — VÉRIFIER QUE LA PRÉVISUALISATION RÉPOND
---------------------------------------------------------------------------
Après lancement, interroger le port et contrôler le code HTTP. Une réponse
de refus d'hôte ou un blocage d'iframe se corrige immédiatement, pas à la
fin de la session.

10. RECETTE ET MISE EN PRODUCTION

10.1 RECETTE FONCTIONNELLE
---------------------------------------------------------------------------
18 scénarios, REC-01 à REC-18, onglet « Recette » du classeur. Chacun est
joué à la gate de sa vague, puis rejoué intégralement avant la mise en
production. Un scénario se joue avec des données réalistes et un compte du
rôle concerné — le RBAC de référence va de N0 (consultation très limitée) à
N4 (administration), sur des périmètres allant de INJS_ENTIER à
PROPRE_COMPTE.

10.2 CONDITIONS DE MISE EN PRODUCTION
---------------------------------------------------------------------------
Ne pas déployer tant qu'un seul de ces points manque :

  [ ] 92 prompts terminés, 10 gates signées
  [ ] 18 scénarios de recette verts, rejoués

Les trois scripts shell ont été exécutés et vérifiés, y compris contre un
projet Django réel de test : bootstrap installe les dépendances et génère
l'overlay ; l'overlay conserve INSTALLED_APPS du projet (relevé :
['django.contrib.contenttypes', 'django.contrib.auth', 'rest_framework',
'demo']) tout en imposant SQLite, ALLOWED_HOSTS=['*'] et le courriel en
mémoire ; probe compte juste une fois les exclusions en place (1 modèle,
1 migration, 2 méthodes de test sur une fixture qui en contient exactement
autant) ; feux-verts retourne 1 sur un feu rouge et 0 quand tout est vert,
et affiche « NON LEVABLE » pour Flutter au lieu de simuler un succès.

workspace : le comportement de ces scripts sur le vrai dépôt
app-injs-lmd2026, en particulier la compatibilité de sa suite de tests avec
SQLite. C'est précisément l'objet de P00-01.
