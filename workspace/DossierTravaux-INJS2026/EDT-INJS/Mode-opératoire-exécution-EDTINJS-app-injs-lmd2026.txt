1.2 INSTALLATION ET VÉRIFICATION DE L'ENVIRONNEMENT DE DÉVELOPPEMENT
----------------------------------------------------------------------------------------------------
À exécuter par chaque exécutant technique, une seule fois.

  # 1. Récupération du dépôt
  git clone <url-du-depot> app-injs-lmd2026demo
  cd app-injs-lmd2026demo
  git checkout main
  git pull

  # 2. Backend — environnement Python 3.12
  cd backend
  python3.12 -m venv .venv
  source .venv/bin/activate
  pip install --upgrade pip
  pip install -r requirements.txt

  # 3. Base de données de développement
  export USE_SQLITE=1          # démarrage rapide ; PostgreSQL recommandé dès que possible
  python manage.py migrate
  python manage.py createsuperuser

  # 4. Contrôle de santé backend — DOIT passer avant toute chose
  python manage.py check
  python manage.py makemigrations --check --dry-run     # doit répondre : aucun changement
  python manage.py test                                  # doit afficher 943 tests, OK

  # 5. Frontend
  cd ../frontend
  npm ci
  npm run lint          # état actuel attendu : 0 erreur, 89 avertissements
  npm run build         # doit réussir

  # 6. Mobile (uniquement pour DM)
  cd ../qr_badge_mobile
  flutter --version     # doit afficher 3.41.7 stable
  flutter pub get --enforce-lockfile
  flutter analyze       # échec connu sur assets/app.env — à corriger en P19

  # 7. Consignation de l'état initial
  # Noter dans docs/EDT_INJS_JOURNAL.md : version Python, Node, Flutter, nombre de tests,
  # nombre d'avertissements ESLint, date. C'est la référence de départ du projet.

  RÈGLE : si l'une de ces étapes échoue, ne pas démarrer P00. Résoudre d'abord, et consigner
  la résolution — elle servira aux prochains arrivants dans l'équipe.

1.3 CRÉATION DE L'ENVIRONNEMENT DE RECETTE
----------------------------------------------------------------------------------------------------
L'audit [S1] §6.3 signale qu'aucun environnement de recette n'existe. Sa création est un prérequis
bloquant de la porte G2 : elle doit donc être engagée dès la phase 0.

  Caractéristiques minimales attendues
    • Même pile que la production : Docker, PostgreSQL 15 ou 16, Redis, Nginx, Gunicorn.
    • Base alimentée par une copie ANONYMISÉE de la production (noms, e-mails, téléphones,
      matricules remplacés ; volumétrie et structure conservées).
    • Accès restreint aux membres du projet et aux référents INJS de la recette.
    • DEBUG à 0, comme en production, pour détecter les comportements dépendant du mode débogage.
    • Déploiement déclenché à chaque fusion dans `main`.
    • Réinitialisable à la demande depuis une copie fraîche, en moins d'une heure.

  Procédure d'anonymisation recommandée (à scripter dans scripts/anonymiser_base.py)
    1. Restaurer le dump de production dans une base temporaire isolée.
    2. Remplacer les données personnelles : noms, prénoms, e-mails, téléphones, adresses,
       matricules, coordonnées bancaires, pièces jointes remplacées par des fichiers factices.
    3. Conserver strictement : volumétrie, structure, relations, dates, statuts, montants
       agrégés — tout ce qui influe sur le comportement et la performance.
    4. Vérifier par sondage qu'aucune donnée nominative ne subsiste.
    5. Consigner la date de la copie et sa version dans le journal.

  RÈGLE : aucune donnée nominative réelle ne transite vers la recette. Cette règle est absolue
  et relève de la protection des données personnelles.

  psql -d injs_lmd_test_restore -c "SELECT COUNT(*) FROM scolarite_dossieretudiant;"

  # 5. Nettoyer
  dropdb injs_lmd_test_restore

    taille du fichier, verdict.

  RÈGLE : une sauvegarde qui n'a jamais été restaurée n'est pas une sauvegarde. Ce test est

1.6 RECUEIL DES DONNÉES DE RÉFÉRENCE AUPRÈS DE L'INJS
----------------------------------------------------------------------------------------------------
C'est le point le plus sous-estimé de tout le projet. Un retard ici bloque P01, P02 et P03,
c'est-à-dire trois prompts du chemin critique. Le recueil démarre en phase 0, pas en semaine 2.

  DEMANDE 1 — CALENDRIER ACADÉMIQUE 2026-2027 (destinataire : RS, échéance : fin S1)
    Éléments attendus :
      • dates de début et de fin de l'année académique ;
      • pour chaque semestre : début des cours, fin des cours, période d'évaluations,
        période d'examens, période de rattrapages, dates de jurys ;
      • vacances et interruptions pédagogiques ;
      • jours fériés retenus par l'institut pour l'année ;
      • jours et heures d'ouverture du campus (le samedi est-il travaillé ?) ;
      • créneaux horaires réellement pratiqués, y compris les créneaux atypiques des activités
        sportives (séances matinales, créneaux piscine, entraînements en fin de journée).
    Format accepté : document, tableur, ou entretien d'une heure avec prise de notes validée.

  DEMANDE 2 — INVENTAIRE DES ESPACES (destinataire : RS, échéance : fin S2)
    Éléments attendus, pour chaque espace :
      • code et nom usuel ;
      • type (salle de cours, TD, TP, amphithéâtre, laboratoire, gymnase, terrain, piscine,
        piste d'athlétisme, salle de musculation, salle de combat, bureau, salle de réunion…) ;
      • localisation : site, zone, bâtiment, niveau ;
      • capacité normale et capacité maximale ;
      • surface si connue ;
      • équipements présents (vidéoprojecteur, tableau, climatisation, wifi, vestiaires,
        gradins, éclairage, matériel sportif, paillasses…) ;
      • état actuel et indisponibilités connues (travaux, maintenance programmée).
    Méthode recommandée : tableur pré-rempli par l'équipe projet à partir des RefSalle existantes,
    puis complété et corrigé sur le terrain par RS, avec une visite physique des installations
    sportives. Prévoir une demi-journée de relevé terrain.

  DEMANDE 3 — RÈGLES DE PLANIFICATION (destinataire : EF et responsables pédagogiques, S5)
    À recueillir en atelier d'une demi-journée :
      • amplitude horaire maximale d'une journée pour un étudiant et pour un enseignant ;
      • pause méridienne obligatoire, et sa plage ;
      • nombre maximal d'heures consécutives d'une même matière ;
      • règles propres aux activités sportives (récupération après séance intense, créneaux
        interdits, contraintes météo, accès à la piscine) ;
      • préférences habituelles des enseignants ;
      • usages tacites à ne pas casser (ce point produit toujours des surprises utiles).

  DEMANDE 4 — COMPLÉTUDE DES MAQUETTES DU PÉRIMÈTRE PILOTE (destinataire : RS, échéance : fin S3)
    Vérifier en base, pour la formation pilote et son semestre :
      • maquette ACTIVE existante, avec UE et ECUE ;
      • volumes horaires CM, TD, TP renseignés pour chaque ECUE ;
      • crédits ECTS renseignés ;
      • affectations enseignant ↔ ECUE réalisées ;
      • groupes créés et étudiants affectés aux groupes.
    Toute lacune constitue un prérequis fonctionnel à faire combler par RS AVANT la semaine 4.

  SUIVI DES DEMANDES
    Chaque demande est tracée dans docs/EDT_INJS_JOURNAL.md avec sa date d'envoi, son échéance,
    son destinataire et son état. Une relance est systématique à J-3 de l'échéance. Un retard de
    plus de 5 jours est escaladé à la Direction (risque X04 du registre).

2. LE CYCLE D'EXÉCUTION D'UN PROMPT — PROCÉDURE PAS À PAS
====================================================================================================

----------------------------------------------------------------------------------------------------
2.1 VUE D'ENSEMBLE DU CYCLE
----------------------------------------------------------------------------------------------------
        ┌─────────────────────────────────────────────────────────────────────┐
        │  1. OUVERTURE            lire, vérifier les entrées, créer la branche│
        │  2. CONCEPTION           note d'une page, validation RT              │
        │  3. SOUMISSION           prompt maître + prompt PXX à l'agent        │
        │  4. DIALOGUE             conduire l'agent, recadrer, itérer          │
        │  5. FINITION             reprise humaine, nettoyage, cohérence       │
        │  6. VÉRIFICATION         batterie de commandes, aucune impasse       │
        │  7. REVUE                un pair, grille imposée                     │
        │  8. VALIDATION           démonstration à EF, verdict                 │
        │  9. CLÔTURE              fusion, recette, journal                    │
        └─────────────────────────────────────────────────────────────────────┘
                  Toute étape sautée se paie plus tard, toujours plus cher.

----------------------------------------------------------------------------------------------------
2.2 ÉTAPE 1 — OUVERTURE DU PROMPT
----------------------------------------------------------------------------------------------------
  Durée : 1 à 2 heures.

  a) Lire, dans cet ordre :
       1. la fiche du prompt dans [D2] §7 (entrées, sorties, déroulé jour par jour, risques) ;
       2. le prompt lui-même dans [D1] (contexte, objectif, à faire, à ne pas faire, livrables) ;
       3. les sections des documents sources citées par le prompt.

  b) Vérifier les critères d'entrée de la fiche. S'il en manque un, NE PAS DÉMARRER : signaler
     le blocage au point quotidien et traiter le prérequis d'abord. Démarrer un prompt sur un
     prérequis manquant est la première cause de reprise de travail.

  c) Créer la branche :
       git checkout main && git pull
       git checkout -b feature/edt-injs-PXX-<libelle-court>

  d) Ouvrir immédiatement une pull request en brouillon, même vide, avec :
       • le titre : « PXX — <intitulé du prompt> » ;
       • la description issue du gabarit (Annexe 2) ;
       • la liste des critères de sortie copiée depuis la fiche [D2] §7.
     Cette PR sert de carnet de bord visible par toute l'équipe pendant l'exécution.

----------------------------------------------------------------------------------------------------
2.3 ÉTAPE 2 — NOTE DE CONCEPTION ET VALIDATION
----------------------------------------------------------------------------------------------------
  Durée : 2 à 4 heures pour les prompts de modélisation (P01 à P05, P12), intégrée pour les autres.
  Cette étape est obligatoire pour : P01, P02, P03, P04, P05, P06, P11, P12, P13.

  Contenu de la note — une page maximum, publiée en commentaire de la PR :
    1. Modèles créés ou étendus : nom, champs principaux, relations, contraintes, index.
    2. Endpoints créés : chemin, méthode, permission, forme de la réponse.
    3. Ponts de rétrocompatibilité : quoi, vers quoi, pilotés par quel drapeau.
    4. Décisions d'architecture : ce qui est retenu, ce qui est écarté, et pourquoi.
    5. Points de vigilance identifiés et leur mitigation.
    6. Estimation du découpage en commits.

  Validation : RT commente la note dans la PR, demande les ajustements nécessaires, puis écrit
  explicitement « Conception validée » avant que la moindre ligne de code ne soit écrite.

  Pourquoi cette étape ne se saute pas : sur le pont Seance ↔ SessionModule (P05) ou sur la
  référence unifiée des personnes (P12), une erreur de conception détectée après trois jours de
  code coûte trois jours. Détectée dans la note, elle coûte dix minutes.

----------------------------------------------------------------------------------------------------
2.4 ÉTAPE 3 — SOUMISSION DU PROMPT À L'AGENT DE CODAGE
----------------------------------------------------------------------------------------------------
  Voir le chapitre 3 pour le détail complet. En résumé :
    a) Ouvrir une session neuve de l'agent, avec le dépôt accessible.
    b) Coller le PROMPT MAÎTRE intégral ([D1] Partie B) — jamais un résumé.
    c) Coller le prompt PXX intégral ([D1] Partie C).
    d) Ajouter le bloc de contexte de session (gabarit au §3.2) : branche, note de conception
       validée, contraintes du jour, périmètre de la sous-tâche.
    e) Demander à l'agent de reformuler sa compréhension AVANT de produire du code. Si la
       reformulation est fausse ou incomplète, corriger immédiatement — ne jamais laisser
       l'agent partir sur une compréhension approximative.

----------------------------------------------------------------------------------------------------
2.5 ÉTAPE 4 — CONDUITE DU DIALOGUE AVEC L'AGENT
----------------------------------------------------------------------------------------------------
  Principe directeur : l'agent produit, l'humain décide. On ne délègue jamais un arbitrage.

  Rythme recommandé
    • Faire produire par lots cohérents : les modèles d'abord, puis les migrations, puis les
      services, puis les tests, puis la documentation. Jamais tout d'un coup.
    • Après chaque lot : relire intégralement le code produit, exécuter les tests, commiter.
    • Ne jamais accumuler plus d'une demi-journée de production non relue.

  Contrôles permanents pendant le dialogue
    ☐ L'agent n'a supprimé aucun fichier existant
    ☐ L'agent n'a pas modifié un modèle existant sans que ce soit demandé
    ☐ Les fichiers produits respectent les seuils de taille (600 lignes / 400 côté frontend)
    ☐ Aucun print() n'est apparu
    ☐ Les messages utilisateur sont en français
    ☐ Les valeurs métier sont en paramètre, pas en dur
    ☐ Les tests écrits testent réellement quelque chose (pas de test tautologique)

  Bonne pratique : commiter après chaque lot validé. Un commit par lot permet de revenir en
  arrière chirurgicalement si l'agent part dans une mauvaise direction au lot suivant.

----------------------------------------------------------------------------------------------------
2.6 ÉTAPE 5 — REPRISE EN MAIN HUMAINE ET FINITION
----------------------------------------------------------------------------------------------------
  L'agent produit un premier jet de qualité variable. La finition humaine est systématique et
  porte sur sept points :

   1. COHÉRENCE DE NOMMAGE — vérifier que les noms de modèles, champs, services et routes sont
      cohérents avec l'existant et entre eux. L'agent tend à varier les conventions.
   2. QUALITÉ DES MESSAGES — relire chaque message d'erreur et d'interface comme le lirait un
      agent de scolarité. Reformuler tout ce qui est technique ou ambigu.
   3. PERTINENCE DES TESTS — supprimer les tests tautologiques, ajouter les cas limites oubliés,
      vérifier que chaque test échoue si l'on casse volontairement le code qu'il teste.
   4. PERFORMANCE — relire chaque requête : select_related, prefetch_related, only, index.
      L'agent produit rarement des requêtes optimisées spontanément.
   5. PERMISSIONS — vérifier qu'aucune route n'est restée sans classe de permission explicite.
   6. TRAÇABILITÉ — vérifier que chaque action sensible écrit bien dans un journal.
   7. DOCUMENTATION — docstrings en français, mise à jour des fichiers docs/ concernés.

  Test de robustesse recommandé (5 minutes, très rentable)
    Casser volontairement une ligne du code produit, relancer les tests : au moins un test doit
    échouer. S'ils passent tous, les tests ne testent rien. Rétablir ensuite la ligne.

----------------------------------------------------------------------------------------------------
2.7 ÉTAPE 6 — BATTERIE DE VÉRIFICATION LOCALE
----------------------------------------------------------------------------------------------------
  Voir le chapitre 4 pour le détail. Aucune PR ne sort du brouillon sans que la batterie
  standard soit intégralement verte.

----------------------------------------------------------------------------------------------------
2.8 ÉTAPE 7 — REVUE PAR UN PAIR
----------------------------------------------------------------------------------------------------
  Durée attendue : 1 à 2 heures pour un prompt moyen, 3 à 4 heures pour P05, P06, P12, P13.

  Procédure pour le demandeur
    a) Sortir la PR du mode brouillon.
    b) Remplir la grille de revue du gabarit : cocher, et commenter chaque point non trivial.
    c) Signaler explicitement au relecteur les 2 ou 3 points sur lesquels on souhaite un
       regard attentif. Un relecteur guidé est un relecteur efficace.

  Procédure pour le relecteur
    a) Lire d'abord la note de conception, puis le code, puis les tests.
    b) Dérouler la grille de [D2] §9.3 point par point, sans en sauter.
    c) Distinguer clairement dans les commentaires :
         BLOQUANT  — doit être corrigé avant la fusion
         IMPORTANT — doit être corrigé, peut faire l'objet d'un commit de suite
         SUGGESTION— amélioration facultative, à noter dans le reste-à-faire si non traitée
    d) Vérifier personnellement au moins un point de non-régression : exécuter soi-même les
       tests de caractérisation, ne pas se contenter du vert affiché par la CI.

  RÈGLE : le relecteur ne se contente jamais d'approuver. S'il n'a aucun commentaire, c'est
  généralement qu'il n'a pas lu assez attentivement. Un prompt de 6 jours produit toujours
  matière à au moins deux remarques.

----------------------------------------------------------------------------------------------------
2.9 ÉTAPE 8 — VALIDATION FONCTIONNELLE
----------------------------------------------------------------------------------------------------
  Durée : 10 à 20 minutes de démonstration, en présence de EF et, selon le prompt, de RS ou RP.

  Déroulé de la démonstration
    a) Rappeler en une phrase l'objectif du prompt.
    b) Dérouler le critère de sortie de la fiche [D2] §7, point par point, en montrant.
    c) Montrer au moins un cas d'erreur et la façon dont le système le présente à l'utilisateur.
       Un système ne se juge pas sur son cas nominal mais sur sa façon d'échouer.
    d) Recueillir le verdict et le consigner séance tenante.

  Les trois verdicts possibles
    ACCEPTÉ ................. tous les critères de sortie sont satisfaits, fusion autorisée.
    ACCEPTÉ AVEC RÉSERVES ... l'essentiel est là, les réserves sont listées, datées, affectées
                              et inscrites dans le reste-à-faire ; la fusion est autorisée.
    REFUSÉ .................. un critère de sortie essentiel n'est pas satisfait ; le prompt
                              retourne en exécution, avec la liste précise de ce qui manque.

  RÈGLE : un verdict n'est jamais implicite. Tant qu'il n'est pas écrit dans le journal, le
  prompt n'est pas terminé.

2.10 ÉTAPE 9 — FUSION, DÉPLOIEMENT EN RECETTE ET CONSIGNATION
----------------------------------------------------------------------------------------------------
  a) Vérifier une dernière fois :
       git checkout main && git pull
       git checkout feature/edt-injs-PXX-<libelle>
       git rebase main            # ou merge selon la convention retenue
       # relancer la batterie de vérification après le rebase — obligatoire

  b) Attendre la CI verte sur la branche rebasée.

  c) Fusionner via l'interface, avec un message de fusion explicite.

  d) Vérifier le déploiement automatique en recette, puis contrôler :
       curl -s https://<recette>/api/health/ | jq .
       # connexion avec un compte de test, un parcours clé du prompt

  e) Consigner dans docs/EDT_INJS_JOURNAL.md, LE JOUR MÊME, selon le gabarit de l'Annexe F
     de [D2]. Une consignation reportée au lendemain est une consignation incomplète.

  f) Mettre à jour docs/EDT_INJS_RESTE_A_FAIRE.md si des réserves ont été émises.

  g) Supprimer la branche de fonctionnalité une fois la fusion vérifiée.

3.4 QUE FAIRE QUAND L'AGENT DÉRAPE — 8 SITUATIONS ET LEUR TRAITEMENT
----------------------------------------------------------------------------------------------------
 SITUATION 1 — L'agent réécrit du code existant au lieu de l'étendre
   Symptôme : des fichiers de `formations` ou `presences` apparaissent modifiés.
   Traitement : `git checkout -- <fichier>` pour rétablir, puis consigne 1 du §3.3.
   Prévention : lister explicitement les fichiers interdits dans le gabarit de session.

 SITUATION 2 — L'agent produit un fichier géant
   Symptôme : un models.py ou un api_views.py de 1 200 lignes.
   Traitement : consigne 2, en imposant le découpage souhaité (un module par famille de modèles).
   Prévention : annoncer dès la soumission la structure de fichiers attendue.

 SITUATION 3 — L'agent invente une règle métier
   Symptôme : un seuil, un arrondi, une transition d'état qui ne figure dans aucun document.
   Traitement : arrêter la session, poser la question à EF, obtenir l'arbitrage, le consigner
   dans docs/EDT_INJS_DECISIONS.md, puis relancer l'agent avec la règle explicite.
   Prévention : préciser dans le gabarit « en cas de doute sur une règle métier, demande-moi ».

 SITUATION 4 — L'agent produit des tests qui ne testent rien
   Symptôme : des assertions triviales, des tests sans cas d'erreur, aucun test de permission.
   Traitement : consigne 8, puis vérifier soi-même par le test de robustesse du §2.6.
   Prévention : demander explicitement « pour chaque fonction : un test nominal, un test limite,
   un test d'erreur, un test de permission ».

 SITUATION 5 — L'agent casse la suite de tests existante
   Symptôme : des tests de `formations` ou `presences` deviennent rouges.
   Traitement : ARRÊT IMMÉDIAT. Ne jamais « adapter » un test existant pour le faire passer.
   Identifier ce qui a changé, rétablir, et reprendre par extension. Si la rupture semble
   inévitable, elle remonte à RT pour arbitrage écrit — c'est la règle R-E de [D2].

 SITUATION 6 — L'agent propose d'installer une dépendance lourde
   Symptôme : ajout de Celery, d'une bibliothèque de calendrier, d'un framework de composants.
   Traitement : refuser par défaut. Toute dépendance nouvelle est un arbitrage de RT, justifié
   par écrit, avec examen du repli en cas d'indisponibilité. Rappel : ortools est la seule
   dépendance nouvelle prévue, et elle doit rester optionnelle.

 SITUATION 7 — L'agent perd le fil sur une session longue
   Symptôme : contradictions avec ce qui a été produit le matin, oubli de contraintes.
   Traitement : clore la session, en ouvrir une neuve, recoller le prompt maître, résumer
   l'état d'avancement et le code déjà produit.

 SITUATION 8 — L'agent produit un résultat plausible mais faux
   Symptôme : le code compile, les tests passent, mais le comportement métier est erroné.
   Traitement : c'est précisément ce que l'étape 8 de validation fonctionnelle doit attraper.
   D'où la règle : on ne fusionne jamais sans démonstration à un humain qui connaît le métier.

----------------------------------------------------------------------------------------------------
Les prompts de plus de 6 JH se découpent systématiquement. Découpage recommandé :

  P05 (8 JH) → 4 sous-tâches : (a) modèles et migrations · (b) machine à états et permissions ·
               (c) pont SessionModule et non-régression · (d) versionnement et journal
  P06 (10 JH) → 5 sous-tâches : (a) contexte et chargement · (b) modèle de décision et

  P11 (10 JH) → déjà découpé en P11(a) lecture et P11(b) action par le plan
  P13 (8 JH) → 4 sous-tâches : (a) jeton et rotation · (b) endpoint de scan et contrôles ·

  Chaque sous-tâche : une session d'agent, un ou plusieurs commits, une vérification locale.

4.6 INTERPRÉTATION DES ÉCHECS ET ARBRE DE DÉCISION
----------------------------------------------------------------------------------------------------
        Un test échoue
              │
              ├─ Est-ce un test que je viens d'écrire ?
              │     OUI → corriger le code ou le test, c'est le travail normal
              │
              ├─ Est-ce un test de caractérisation (P00) ?
              │     OUI → ARRÊT. Règle R-E. Ne jamais adapter le test.
              │            Identifier le changement de comportement, rétablir,
              │            et si la rupture semble inévitable : arbitrage écrit de RT.
              │
              ├─ Est-ce un test existant d'une autre application ?
              │     OUI → forte présomption de régression. Même traitement que ci-dessus.
              │
              └─ Est-ce un échec intermittent ?
                    OUI → ne jamais relancer en espérant que ça passe. Identifier la cause
                          (dépendance à l'ordre, à l'horloge, à un état partagé) et la corriger.
                          Un test instable est un test à réparer, pas à ignorer.

        La CI échoue mais le local passe
              → Vérifier : version de Python ou de Node, base PostgreSQL contre SQLite,
                fuseau horaire, variables d'environnement, ordre d'exécution des tests,
                fichiers non commités. Reproduire en local dans les conditions de la CI.

        Le bench se dégrade
              → Identifier le commit responsable par bisection, profiler la vue concernée,
                corriger avant de poursuivre. Une dégradation acceptée devient permanente.

5.1 DÉROULEMENT D'UNE SÉANCE DE PORTE
----------------------------------------------------------------------------------------------------
  Durée : 2 heures pour G0 et G1, une demi-journée pour G2 et G3.
  Participants : RT (préside), DB, EF, plus DF/DM/RS/EX selon la porte.
  Préparation : la veille, RT diffuse la liste des points à contrôler et l'état déclaré de chacun.

  Déroulé
    1. Rappel de l'objectif de la porte et de ce qu'elle protège (10 min).
    2. Contrôle point par point de la check-list, EN EXÉCUTANT réellement les vérifications à
       l'écran. Un point déclaré satisfait mais non démontré est réputé non satisfait (60 à 120 min).
    3. Relevé des points non satisfaits, avec responsable et échéance (15 min).
    4. Décision : PORTE FRANCHIE / FRANCHIE SOUS CONDITION / NON FRANCHIE (10 min).
    5. Consignation immédiate dans docs/EDT_INJS_JOURNAL.md, signée par RT et EF.

  Les trois décisions possibles
    FRANCHIE ............... tous les points sont satisfaits. L'itération suivante démarre.
    FRANCHIE SOUS CONDITION  au plus deux points mineurs restent, avec échéance sous 5 jours
                             et responsable nommé. L'itération suivante démarre, mais les
                             conditions sont vérifiées avant la porte suivante.
    NON FRANCHIE ........... un point structurant manque. L'itération suivante ne démarre pas.
                             Voir §5.6.

5.6 QUE FAIRE EN CAS DE PORTE NON FRANCHIE
----------------------------------------------------------------------------------------------------
  1. Ne pas démarrer l'itération suivante. C'est la règle, et elle protège le projet.
  2. Établir séance tenante la liste précise des points manquants, avec pour chacun : le
     responsable, l'effort estimé, l'échéance.
  3. Décider du mode de rattrapage :
       • rattrapage court (≤ 3 jours) : on comble, on repasse la porte, on poursuit ;
       • rattrapage long (> 3 jours) : on applique l'arbitrage de périmètre de l'Annexe E de
         [D2], on réduit le contenu de l'itération suivante, et on informe la Direction sous 48 h.
  4. Consigner la non-franchissement, sa cause et la décision dans le journal. Ce n'est pas un
     échec à masquer : c'est une information de pilotage.
  5. En rétrospective, chercher pourquoi le manque n'a pas été détecté plus tôt.

7.3 RÈGLES DE CONDUITE EN DÉMONSTRATION
----------------------------------------------------------------------------------------------------
  • Parler métier, jamais technique. On ne dit pas « le sérialiseur renvoie un 409 », on dit
    « le système signale que la séance a été modifiée entre-temps et invite à recharger ».
  • Montrer les limites de son plein gré. Une limite annoncée est une limite acceptée ; une
    limite découverte par l'auditoire est un problème de crédibilité.
  • Ne jamais improviser une fonction non préparée, même sur demande insistante. Noter la
    demande, la traiter dans le registre, y répondre à la démonstration suivante.
  • Si un incident survient en direct : l'assumer calmement, basculer sur le plan de secours,
    et l'analyser en rétrospective. Cela arrive, et ce n'est pas grave si c'est bien géré.
  • Terminer systématiquement par : ce qui vient ensuite, et ce qu'on attend de l'auditoire.

8. MODE OPÉRATOIRE DE LA RECETTE
====================================================================================================

----------------------------------------------------------------------------------------------------
8.1 ORGANISATION D'UNE SESSION DE RECETTE
----------------------------------------------------------------------------------------------------
  Cadre
    • Lieu : salle équipée, avec un poste par recetteur et une connexion représentative.
    • Durée : demi-journée par session, 3 sessions pour couvrir les 60 scénarios.
    • Participants : EF (anime), RS et RP (exécutent), DB (observe et note, n'intervient pas).
    • Environnement : recette uniquement, jamais la production.
    • Données : jeu de démonstration réaliste, avec les vrais intitulés de l'INJS.

  Règle d'or de la recette : l'équipe technique OBSERVE et NOTE, elle n'aide pas. Si le
  recetteur ne trouve pas, c'est une anomalie d'ergonomie, pas une erreur de l'utilisateur.
  Cette règle est difficile à tenir et pourtant c'est elle qui produit le plus de valeur.

----------------------------------------------------------------------------------------------------
8.2 EXÉCUTION D'UN SCÉNARIO DE RECETTE
----------------------------------------------------------------------------------------------------
  Chaque scénario est décrit et renseigné selon ce cadre :

    Identifiant ........ RC-xx
    Domaine ............ <ex. Émargement manuel et forçage>
    Acteur ............. <rôle utilisé pour le test>
    Préconditions ...... <état du système avant>
    Étapes ............. 1. … 2. … 3. …
    Résultat attendu ... <ce que l'utilisateur doit voir ou obtenir>
    Résultat observé ... <à renseigner pendant l'exécution>
    Verdict ............ CONFORME / NON CONFORME / BLOQUÉ / NON TESTÉ
    Anomalie ........... <référence si non conforme>
    Testeur, date ...... <nom, date>

  Conseils d'exécution
    • Exécuter les scénarios dans l'ordre, sans en sauter.
    • Noter le temps mis par le recetteur : un scénario qui prend trois fois plus longtemps que
      prévu révèle un problème, même s'il aboutit.
    • Noter les hésitations et les questions à voix haute : ce sont des indices d'ergonomie.
    • Ne pas corriger une anomalie pendant la session : noter, poursuivre, traiter après.

----------------------------------------------------------------------------------------------------
8.3 TRAITEMENT DES ANOMALIES DÉTECTÉES
----------------------------------------------------------------------------------------------------
  Qualification par EF, immédiatement après la session :
    A1 BLOQUANTE ...... empêche l'usage. Corrigée avant la fin de l'itération, sans discussion.
    A2 MAJEURE ........ contournement pénible existant. Corrigée avant la porte suivante.
    A3 MINEURE ........ gêne légère. Planifiée dans le reste-à-faire.
    A4 COSMÉTIQUE ..... confort. Traitée si le temps le permet, après V3 sinon.

  Chaque anomalie est enregistrée avec : identifiant, scénario d'origine, description précise,
  capture d'écran, gravité, responsable, échéance, état. Suivi dans docs/EDT_INJS_INCIDENTS.md.

  Après correction : le scénario est intégralement rejoué, pas seulement l'étape corrigée.

----------------------------------------------------------------------------------------------------
8.4 CONDUITE DES 6 SCÉNARIOS DE RECETTE TERRAIN
----------------------------------------------------------------------------------------------------
  Ces scénarios se déroulent en conditions réelles, dans les locaux et sur les installations
  sportives de l'INJS Marcory. Ils conditionnent le passage de la vague V1 à la vague V2.

  PRÉPARATION COMMUNE
    ☐ Prévenir l'enseignant et les étudiants concernés, obtenir leur accord
    ☐ Prévoir la feuille d'émargement papier de secours, imprimée
    ☐ Prévoir un téléphone de secours chargé
    ☐ Un observateur de l'équipe projet est présent, avec de quoi noter
    ☐ Convenir à l'avance du signal d'arrêt en cas de perturbation du cours

  T1 — COURS MAGISTRAL EN AMPHITHÉÂTRE, 120 ÉTUDIANTS, QR PROJETÉ
    Observer : temps total d'émargement de 120 étudiants, lisibilité du QR depuis le fond de
    l'amphithéâtre, nombre d'échecs de scan, comportement du compteur en direct, charge serveur.
    Critère : émargement complet en moins de 5 minutes, moins de 5 % d'échecs.

  T2 — TP EN LABORATOIRE, 20 ÉTUDIANTS, SCAN INVERSE DES BADGES
    Observer : fluidité du scan des cartes par l'enseignant, retour sonore et visuel, gestion
    des étudiants sans carte.
    Critère : 20 étudiants scannés en moins de 3 minutes.

  T3 — SÉANCE D'ATHLÉTISME SUR LA PISTE, RÉSEAU DÉGRADÉ
    Observer : comportement de l'application en réseau instable, mise en file des scans,
    lisibilité de l'écran en plein soleil, autonomie de la batterie, synchronisation au retour.
    Critère : aucun scan perdu, indicateur de synchronisation compris par l'enseignant.

  T4 — SÉANCE DE NATATION, TÉLÉPHONES INTERDITS AU BORD DU BASSIN
    Observer : émargement manuel intégral par l'encadrant depuis le vestiaire ou avant l'entrée,
    usage du forçage motivé, praticité réelle.
    Critère : émargement complet sans matériel au bord du bassin, motifs pertinents disponibles.

  T5 — PANNE RÉSEAU TOTALE PENDANT UNE SÉANCE
    Déroulé : couper volontairement l'accès pendant la séance, basculer sur la feuille papier,
    puis saisir a posteriori avec forçage en lot motivé.
    Observer : disponibilité de la feuille papier, facilité de la saisie a posteriori, qualité
    de la trace produite.
    Critère : présence de tous les étudiants correctement enregistrée dans les 24 heures, avec
    motif unique en lot et journal complet.

  T6 — ANNULATION D'UNE SÉANCE PUBLIÉE LA VEILLE
    Observer : réception effective des notifications par les étudiants et l'enseignant, délai,
    clarté du message, programmation du rattrapage.
    Critère : tous les concernés informés en moins de 5 minutes, rattrapage programmé sans conflit.

  RESTITUTION
    Chaque scénario terrain fait l'objet d'un compte rendu d'une page : conditions réelles,
    déroulé, chiffres relevés, anomalies, verdict, recommandations. Ces comptes rendus sont
    présentés en comité de pilotage avant la décision de passage en vague V2.

10. MODE OPÉRATOIRE DES INCIDENTS ET DU REPLI
====================================================================================================

----------------------------------------------------------------------------------------------------
10.1 QUALIFICATION D'UN INCIDENT EN 4 GRAVITÉS
----------------------------------------------------------------------------------------------------
  G1 CRITIQUE ... L'émargement est impossible en séance, ou une donnée de présence est perdue,
                  ou le service est indisponible en heures ouvrées.
                  Prise en charge immédiate. Contournement proposé sous 15 minutes.
                  Résolution ou repli sous 4 heures ouvrées. Information de la Direction.
  G2 MAJEUR ..... Une fonction essentielle est dégradée mais contournable.
                  Prise en charge dans la journée. Résolution sous 1 jour ouvré.
  G3 MINEUR ..... Gêne ou comportement inattendu sans blocage.
                  Planifié dans l'itération suivante.
  G4 COSMÉTIQUE . Confort, présentation. Traité si le temps le permet.

----------------------------------------------------------------------------------------------------
10.2 RÉFLEXES DES 5 PREMIÈRES MINUTES
----------------------------------------------------------------------------------------------------
   1. CONSTATER — reproduire l'incident, noter l'heure exacte, l'utilisateur, l'action, le message.
   2. PROTÉGER — si une donnée est en jeu, arrêter l'écriture avant toute autre chose. En cas de
      doute, désactiver le drapeau concerné : le repli de niveau 1 est réversible et sans risque.
   3. CONTOURNER — donner immédiatement une solution à l'utilisateur : feuille papier, émargement
      manuel, saisie a posteriori. L'utilisateur ne doit jamais rester bloqué.
   4. ALERTER — informer RT et EF. Ne jamais traiter seul un incident de gravité 1.
   5. TRACER — ouvrir la fiche d'incident immédiatement, même incomplète.

  Ce qu'il ne faut jamais faire : modifier la production dans l'urgence sans sauvegarde, relancer
  plusieurs fois en espérant que cela passe, ou supprimer des données « pour débloquer ».

----------------------------------------------------------------------------------------------------
10.3 EXÉCUTION DU REPLI PAR NIVEAU
----------------------------------------------------------------------------------------------------
 NIVEAU 1 — REPLI FONCTIONNEL (moins d'une minute) — À PRIVILÉGIER TOUJOURS
   python manage.py edt_injs_drapeau --nom <DRAPEAU> --valeur 0 \
       --motif "Incident <référence> — repli d'urgence"
   Vérifier immédiatement le retour au comportement antérieur. Informer les utilisateurs.

 NIVEAU 2 — REPLI APPLICATIF (5 à 15 minutes)
   git checkout <étiquette-version-précédente>
   python manage.py collectstatic --noinput
   docker compose up -d --build app cron
   curl -s https://<prod>/api/health/ | jq .
   Les migrations additives restent en place : elles sont compatibles avec la version antérieure.

 NIVEAU 3 — REPLI DE DONNÉES (30 à 60 minutes)
   bash scripts/backup_injs_lmd.sh          # sauvegarder AVANT de modifier quoi que ce soit
   python manage.py migrer_edt_vers_edt_injs --rollback --run-id <identifiant> --dry-run
   # examiner le rapport, puis seulement ensuite :
   python manage.py migrer_edt_vers_edt_injs --rollback --run-id <identifiant>
   python manage.py edt_injs_reconcilier_presences --controle-seul

 NIVEAU 4 — RESTAURATION COMPLÈTE (1 à 2 heures) — DERNIER RECOURS
   Décision de RT avec information immédiate de la Direction.
   Arrêt du service, restauration de la sauvegarde vérifiée la plus récente, contrôle d'intégrité,
   redémarrage, communication aux utilisateurs sur la fenêtre de données perdue.
   Analyse de cause racine écrite sous 48 heures, obligatoire.

----------------------------------------------------------------------------------------------------
10.4 ANALYSE DE CAUSE RACINE
----------------------------------------------------------------------------------------------------
  Obligatoire pour tout incident de gravité 1 ou 2, sous 48 heures, en une page :
    • Chronologie factuelle : détection, actions, résolution, horaires précis.
    • Impact : utilisateurs touchés, données concernées, durée.
    • Cause immédiate : ce qui a techniquement échoué.
    • Cause profonde : pourquoi cela n'a pas été détecté avant. C'est la partie la plus utile.
    • Actions correctives : ce qui est corrigé.
    • Actions préventives : le test, le contrôle ou la procédure ajoutés pour que cela ne se
      reproduise pas. Chaque incident de gravité 1 doit produire au moins un test automatisé.
    • Responsable et échéance de chaque action.

  L'analyse est présentée en rétrospective. On cherche la faiblesse du processus, jamais le
  responsable individuel : une culture de la recherche de coupable produit des incidents cachés.

12. MODE OPÉRATOIRE EN ÉQUIPE RÉDUITE (UN SEUL EXÉCUTANT)
====================================================================================================

Si le projet est conduit par une seule personne polyvalente, l'horizon passe de 20 à 32 semaines
et les adaptations suivantes s'appliquent. Les portes de qualité, elles, restent inchangées.

 12.1 ORDONNANCEMENT
   Exécution strictement en série : P00 → P01 → … → P22. Aucune parallélisation.
   Le découpage P11(a)/P11(b) et P17(a)/P17(b) reste pertinent : il permet de valider l'API
   avant de construire dessus.

 12.2 REVUE PAR UN PAIR — LE POINT LE PLUS DÉLICAT
   Sans second développeur, la revue se remplace par trois pratiques cumulatives :
     • Relecture différée : ne jamais relire son propre code le jour où on l'a écrit. Relire le
       lendemain matin, avant toute autre tâche. Le regard est différent et attrape beaucoup.
     • Relecture guidée par la grille : dérouler la grille de [D2] §9.3 point par point, à voix
       haute, en cochant. Le formalisme compense l'absence de second regard.
     • Revue externe périodique : faire relire par un tiers compétent, même extérieur au projet,
       les prompts les plus sensibles : P05 (pont SessionModule), P13 (sécurité QR), P14 (audit),
       P22 (migration). Une demi-journée de revue externe sur ces quatre prompts est un
       investissement très rentable.

 12.3 VALIDATION FONCTIONNELLE
   Elle reste OBLIGATOIRE et ne peut pas être auto-administrée. Le référent scolarité de l'INJS
   doit voir et valider. Si aucun référent n'est disponible, le projet doit être suspendu : un
   système de gestion académique validé par son seul développeur est un système qui sera rejeté
   à la mise en service.

 12.4 RYTHME
   • Alterner les natures de tâche : une journée de modèles, une journée de tests, une journée
     d'interface. La monotonie produit des erreurs.
   • Ne jamais enchaîner deux prompts sans faire la consignation du premier.
   • Prévoir une demi-journée de consolidation à la fin de chaque prompt : documentation,
     nettoyage, reste-à-faire.

 12.5 CE QUI NE SE NÉGOCIE PAS, MÊME SEUL
   • La batterie de vérification complète avant chaque fusion.
   • Les tests de caractérisation verts.
   • La consignation au journal le jour même.
   • Les portes de qualité, avec au minimum la présence du référent fonctionnel.
   • La validation fonctionnelle par un utilisateur métier.
   • La procédure de repli testée avant chaque bascule.

13. FICHE RÉFLEXE — L'ESSENTIEL SUR UNE PAGE
====================================================================================================

 AVANT DE COMMENCER UN PROMPT
   Lire la fiche [D2] §7 → vérifier les entrées → créer la branche → ouvrir la PR en brouillon
   → écrire la note de conception → la faire valider.

 POUR SOUMETTRE À L'AGENT
   Prompt maître intégral + prompt PXX intégral + gabarit de session (§3.2)
   → demander une reformulation → confirmer → produire par lots → relire chaque lot → commiter.

 AVANT DE SORTIR DU BROUILLON
   check → makemigrations --check → migrate (vide + peuplée) → rollback → test → caractérisation
   → lint → build → test frontend → analyze → bench.

 AVANT DE FUSIONNER
   Revue par un pair avec la grille → validation fonctionnelle par EF → CI verte après rebase.

 APRÈS AVOIR FUSIONNÉ
   Vérifier la recette → consigner au journal LE JOUR MÊME → mettre à jour le reste-à-faire
   → supprimer la branche.

 EN CAS DE DOUTE SUR UNE RÈGLE MÉTIER
   Ne pas trancher soi-même. Ne pas laisser l'agent trancher. Demander à EF, obtenir l'arbitrage,
   le consigner dans EDT_INJS_DECISIONS.md.

 EN CAS DE TEST EXISTANT QUI CASSE
   ARRÊT. Ne jamais adapter le test. Identifier la régression, rétablir, ou arbitrage écrit de RT.

 EN CAS D'INCIDENT EN PRODUCTION
   Constater → protéger (désactiver le drapeau) → contourner pour l'utilisateur → alerter → tracer.

 EN CAS DE RETARD
   Ne jamais réduire la qualité. Réduire le périmètre selon l'ordre de l'Annexe E de [D2].
   Jamais réductibles : tests de non-régression, traçabilité, forçage motivé, sécurité QR,
   permissions, réversibilité, feuille d'émargement papier.

 LA QUESTION À SE POSER CHAQUE SOIR
   « Si je déployais en production demain matin, est-ce que l'INJS pourrait fonctionner ? »
   Si la réponse n'est pas un oui franc, c'est qu'il reste quelque chose à faire avant d'avancer.

RAPPEL FINAL
====================================================================================================
Ce mode opératoire ne vaut que s'il est réellement suivi. Les procédures qu'il décrit ne sont pas
des formalités : chacune découle d'un risque identifié sur ce projet précis. La note de conception
protège du code à refaire. La batterie de vérification protège de la régression. La validation
fonctionnelle protège du système techniquement juste et métier faux. La consignation protège de
l'oubli. La procédure de repli protège l'INJS le jour où quelque chose se passe mal — et ce jour
arrive toujours.

L'objectif n'est pas de suivre un processus. L'objectif est que, chaque matin de l'année
académique, un enseignant de l'INJS Marcory puisse ouvrir sa séance, que ses étudiants puissent
badger, et que personne n'ait à se demander si le système va tenir.
