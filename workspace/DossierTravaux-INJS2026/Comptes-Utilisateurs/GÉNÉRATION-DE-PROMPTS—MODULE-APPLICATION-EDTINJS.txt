0. MODE D'EMPLOI DE CE FICHIER
================================================================================
Ce fichier contient une suite de prompts autonomes, exécutables dans l'ordre par un
agent de développement (Agent Mode / Cline) travaillant sur le dépôt
`app-injslmd2026demo`.
RÈGLES D'USAGE
  1. Exécuter les prompts UN PAR UN, dans l'ordre P0 → P9.
  2. Chaque prompt est COPIÉ-COLLÉ INTÉGRALEMENT, précédé :
        - des 4 pièces sources (§1) jointes au prompt ;
        - du bloc de contexte commun « BC-EDT » (§3) si l'agent n'a pas déjà lu ce
          fichier en entier ;
        - de la directive de conduite (§2).
  3. Ne jamais lancer P(n+1) avant que P(n) soit terminé, vérifié, commité et que son
     rapport final (§6) soit produit.
  4. À chaque prompt, l'application doit rester FONCTIONNELLE, OPÉRATIONNELLE et
     PERFORMANTE : aucune étape ne doit laisser le dépôt dans un état non testable.
  5. Les prompts supposent que l'agent connaît le dépôt ; ils lui interdisent
     explicitement d'inventer un fichier, un modèle, une route ou un test.
LIVRABLE DE CHAQUE PROMPT : code + migrations + tests + documentation + rapport final.

2. DIRECTIVE DE CONDUITE (à rappeler à chaque prompt)
================================================================================
  comprendre → décider → exécuter → vérifier → livrer.
  Zéro détour ; zéro question dont la réponse est dans le dépôt ;
  modification MINIMALE, ADDITIVE et RÉVERSIBLE ;
  aucune affirmation non prouvée (test, commit, mesure) ;
  aucune opération destructive (DROP / TRUNCATE / reset --hard / clean -fd /
  réinitialisation de base / suppression de données de démonstration) ;
  la sécurité et l'intégrité des données priment sur la rapidité ;
  le backend est la SEULE autorité d'autorisation (le masquage d'un bouton front
  n'est jamais une mesure de sécurité) ;
  français partout : code, commentaires, journaux, documentation, écrans ;
  l'application doit rester fonctionnelle, opérationnelle et performante après chaque prompt.
  PRIORITÉ EN CAS DE CONFLIT :
  1) sécurité et intégrité des données ; 2) règles métier INJS-LMD ; 3) exactitude
  technique ; 4) stabilité du projet ; 5) tests et vérification ; 6) rapidité ;
  7) documentation et confort.

PROMPT P1 — RÉFÉRENTIEL TEMPOREL ET STRUCTUREL DE PLANIFICATION
--------------------------------------------------------------------------------
OBJECTIF : doter le module EDT-INJS du référentiel nécessaire à toute planification
fiable (temps académique, espaces, disponibilités), sans modifier les comportements
existants.
PÉRIMÈTRE INCLUS
- Référentiel temporel : semestres/periodes académiques exploitables par l'EDT,
  semaines académiques numérotées, jours fériés et périodes de vacances.
- Créneaux types normalisés (matin/après-midi/soirée), cohérents avec
  `edts.CreneauTemplate` (ne pas casser l'existant).
- Disponibilités/indisponibilités des enseignants : réutiliser
  `scolarite.IndisponibiliteEnseignant` ; ajouter si nécessaire la granularité
  horaire (jour + plage) — additif.
- Espaces : lecture de `formations.RefSalle`/`RefBatiment`/`RefSite`, capacité,
  équipements, `type_espace`, indisponibilités (`indisponible_du`/`au`) ; ALIGNEMENT
  avec `patrimoine.ReservationEspace` (aucune duplication de moteur de réservation).
- Occupation des espaces : service de consultation unifiant séances planifiées +
  réservations validées + occupations connues (épreuves de concours) — LECTURE seule.
HORS PÉRIMÈTRE : génération automatique d'EDT (P2), séances datées (P3), présences (P4/P5).
MODÈLE DE DONNÉES (règles)
- Toute nouveauté est additive, dans l'app `edts` (ou `scolarite` si le modèle y vit
  déjà), avec FK `on_delete=PROTECT` ou `SET_NULL` — jamais CASCADE sur une donnée
  pédagogique existante.
- Contraintes d'unicité explicites (ex. pas deux périodes de mêmes bornes pour une même
  année académique).
- Migrations réversibles, idempotentes, sans perte de données.
API (additive)
- `GET /api/edts/periodes/`, `GET /api/edts/periodes/<pk>/`,
  `GET /api/edts/jours-feries/`, `GET /api/edts/disponibilites/?enseignant=` ,
  `GET /api/edts/occupation-espace/?salle=&date_debut=&date_fin=`.
- Permissions : lecture pour tout compte authentifié ; écriture réservée via
  `IsEdtPlanification` (réutiliser `edts/permissions.py`).
- Aucune rupture du contrat `/api/scolarite/edt/` (v1.1) : ajouts uniquement, sinon feu
  de versionnement documenté (`docs/EDT_CONTRAT_DONNEES.md`).
SÉCURITÉ : cloisonnement par secrétariat respecté pour les rôles non globaux ;
pas d'exposition nominative inutile ; champs de traçabilité (créé/modifié par, horodatage).
TESTS (créer `backend/edts/tests/` — ≥ 15 tests, succès ET refus)
- contraintes d'unicité et de validation (plages inversées, chevauchements) ;
- numérotation des semaines et bornes de période ;
- indisponibilité chevauchante détectée ;
- occupation d'espace combinant séances + réservations validées + occupations connues ;
- permissions : lecture 200, écriture 403 pour un rôle non planificateur, 401 anonyme ;
- additivité : le contrat `/api/scolarite/edt/` reste bit-à-bit compatible (tests
  existants verts).
COMMANDES DE VÉRIFICATION
  cd backend && python manage.py test edts scolarite.tests.test_edt_export scolarite.tests.test_edt_extensions -v 2
  python manage.py test --noinput
  python manage.py check_repo_hygiene && python manage.py export_api_contract --check
  python manage.py smoke_test_injs
  cd ../frontend && npm run lint && npm run test:coverage && npm run build
CRITÈRES D'ACCEPTATION : référentiel exploitable par l'API, migrations réversibles
testées, aucun écran ni comportement existant modifié, tests verts, contrat d'API vert.
REPLI : `migrate edts <migration_précédente>` ; les nouvelles routes se désactivent en
retirant leur entrée d'URL (aucun consommateur en P1).
RAPPORT FINAL : au gabarit §6.

PROMPT P2 — MOTEUR NATIF DE PLANIFICATION (GÉNÉRATION, CONFLITS, VALIDATION)
--------------------------------------------------------------------------------
OBJECTIF : livrer le moteur natif complémentaire prévu par l'ADR-003 : produire des
BROUILLONS d'emploi du temps contraints, détecter et expliquer les conflits, faire
valider puis publier par un rôle habilité — sans jamais court-circuiter le planificateur
externe.
PÉRIMÈTRE INCLUS
- Consolidation du modèle : rattacher proprement les affectations aux référentiels
  (`RefSalle` en plus de `salle_nom`, `Formateur` en plus de `enseignant_id`) par ajout
  de FK NULLABLE + maintien des champs texte legacy (compatibilité, ADR-005/ADR-001).
  Toute migration de données est additive et idempotente (jamais de suppression de colonne).
- Génération assistée de brouillon : proposer un placement des volumes horaires
  (`formations.Module.duree_prevue_heures`, maquettes/ECUE, groupes, effectifs) sur les
  créneaux disponibles, en respectant : capacité de salle, disponibilités enseignants,
  occupations d'espaces, plages de période, une seule séance simultanée par groupe,
  par enseignant et par salle.
