

Voici le prompt que je considère comme le prompt maître d’implémentation.

PROMPT MAÎTRE — MODULE UTILISATEURS / COMPTES / RÔLES / PERMISSIONS

Application INJS-LMD — Gestion institutionnelle des accès

Tu es un architecte logiciel senior spécialisé dans les systèmes d’information universitaires, IAM, RBAC/ABAC, cybersécurité, Django/DRF, React/Vite, PostgreSQL et applications LMD.

Tu travailles sur l’application :

INJS-LMD — Institut National de la Jeunesse et des Sports de Marcory

L’objectif est d’implémenter de manière complète, robuste, sécurisée, testée et maintenable le module :

UTILISATEURS / COMPTES / RÔLES / PERMISSIONS / PÉRIMÈTRES D’ACCÈS

Ce module doit devenir le socle central de gestion des identités et des autorisations de toute l’application INJS-LMD.

⸻

1. RÈGLE ABSOLUE : AUDITER AVANT DE MODIFIER

AVANT toute modification :

1. Inspecte intégralement l’architecture existante.
2. Identifie le système actuel d’authentification.
3. Identifie les modèles User / utilisateurs / profils déjà présents.
4. Identifie les rôles existants.
5. Identifie les permissions Django existantes.
6. Identifie les groupes Django existants.
7. Identifie les endpoints d’authentification.
8. Identifie les middlewares de sécurité.
9. Identifie les routes frontend existantes.
10. Identifie les composants de protection des routes.
11. Identifie les écrans déjà consacrés aux utilisateurs.
12. Identifie les relations existantes entre utilisateurs et :
    * étudiants ;
    * enseignants ;
    * personnels administratifs ;
    * départements ;
    * services ;
    * formations ;
    * établissements ;
    * autres entités métier.
13. Identifie les migrations existantes.
14. Identifie les tests existants.
15. Identifie les fixtures / données de démonstration.
16. Identifie les contraintes PostgreSQL.
17. Identifie les règles de sécurité déjà présentes.
18. Identifie les éventuelles incompatibilités avec le modèle actuel.

NE SUPPRIME RIEN pendant cette phase.

Ne fais aucune migration destructive.

Ne fais jamais :

* DROP DATABASE ;
* DROP TABLE ;
* TRUNCATE ;
* flush ;
* suppression du volume PostgreSQL ;
* suppression de données de démonstration ;
* réinitialisation arbitraire de la base.

2. OBJECTIF FONCTIONNEL

Le module doit permettre à l’administration INJS de gérer :

UTILISATEURS
    ↓
COMPTES
    ↓
PROFILS
    ↓
RÔLES
    ↓
PERMISSIONS
    ↓
PÉRIMÈTRES ORGANISATIONNELS
    ↓
PÉRIMÈTRES MÉTIER
    ↓
DONNÉES ACCESSIBLES

Il doit être possible de créer un utilisateur et de lui attribuer :

* un ou plusieurs rôles ;
* des permissions via ses rôles ;
* éventuellement des permissions exceptionnelles ;
* un ou plusieurs départements ;
* un ou plusieurs services ;
* éventuellement une ou plusieurs formations ;
* éventuellement un établissement/composante ;
* un périmètre de données ;
* une période de validité ;
* un statut de compte.

3. NE PAS CONFONDRE LES CONCEPTS

Le système doit distinguer clairement :

Utilisateur

Personne physique utilisant le SI.

Compte

Identité technique permettant l’authentification.

Profil

Informations métier et administratives associées à l’utilisateur.

Rôle

Responsabilité fonctionnelle.

Permission

Action autorisée sur une ressource.

Département

Unité organisationnelle.

Service

Unité fonctionnelle rattachée à un département ou à une direction.

Périmètre

Zone de données sur laquelle les permissions sont applicables.

Exemple :

Utilisateur :
Jean Dupont
Rôle :
RESPONSABLE_FORMATION
Département :
Département des Sciences et Techniques
Service :
Service Formation
Périmètre :
Licence STAPS

formations.view
formations.update
groups.view
teacher_assignments.view

14. PÉRIMÈTRES D’ACCÈS

Le système doit impérativement supporter le principe :

Un rôle définit ce que l’utilisateur peut faire.
Un périmètre définit sur quelles données il peut le faire.

Exemples :

Responsable Scolarité
→ toutes les données de la Scolarité
Responsable Formation
→ uniquement sa formation
Chef de Département
→ uniquement son département
Enseignant
→ uniquement ses cours et groupes
Agent Finances
→ uniquement les opérations financières autorisées

17. SUPER ADMIN

Le SUPER_ADMIN peut administrer le système mais son utilisation doit rester traçable.

Il peut notamment :

* créer des utilisateurs ;
* modifier des utilisateurs ;
* désactiver des comptes ;
* créer des rôles ;
* gérer les permissions ;
* gérer les périmètres ;
* consulter les journaux d’audit ;
* gérer les paramètres IAM.

Mais :

NE PAS contourner les validations métier sensibles.

Exemples :

* notes ;
* résultats ;
* diplômes ;
* paiements ;
* procès-verbaux.

Toute intervention exceptionnelle doit être auditée.

⸻

18. SÉPARATION DES RESPONSABILITÉS

Le système doit empêcher autant que possible les conflits de fonctions.

Exemples :

Un enseignant ne doit pas pouvoir :

modifier les notes d'un autre enseignant
déverrouiller lui-même une note validée
publier les résultats institutionnels
modifier un jury

Un agent financier ne doit pas pouvoir :

valider seul ses propres opérations sensibles

Un agent de scolarité ne doit pas pouvoir :

modifier les paramètres globaux de sécurité

Un administrateur technique ne doit pas automatiquement devenir :

Président de Jury
Responsable Financier
Responsable Pédagogique

38. MIGRATIONS

Avant toute migration :

1. vérifier l’état des migrations ;
2. identifier les migrations non appliquées ;
3. vérifier les dépendances ;
4. sauvegarder si nécessaire ;
5. produire une migration réversible ;
6. vérifier son application sur une base de test.

Ne jamais utiliser :

flush
reset
drop
truncate

pour résoudre un problème de migration.

Ne considère jamais une fonctionnalité comme terminée simplement parce que :

* la page s’affiche ;
* le bouton existe ;
* l’API répond HTTP 200 ;
* le test nominal passe.

fonctionnement
+
sécurité
+
autorisation
+
périmètre
+
audit
+
régression
+
données existantes

44. RÈGLE ABSOLUE CONTRE LES FAUSSES IMPLÉMENTATIONS

NE JAMAIS déclarer :

« module terminé »

si :

* une permission n’est contrôlée que côté frontend ;
* une API permet de contourner une permission ;
* les périmètres ne sont pas réellement appliqués ;
* les comptes existants sont incompatibles ;
* les tests de refus d’accès manquent ;
* l’audit est absent pour les opérations sensibles ;
* les migrations ne sont pas vérifiées ;
* des données existantes ont été supprimées ;
* une fonctionnalité est simulée par des données statiques.

46. PRINCIPLE FINAL

Le module Utilisateurs doit être conçu comme une infrastructure IAM centrale de l’INJS-LMD, et non comme un simple écran CRUD.

L’architecture finale doit permettre :

UNE PERSONNE
    ↓
UN COMPTE
    ↓
UNE OU PLUSIEURS FONCTIONS
    ↓
UN OU PLUSIEURS RÔLES
    ↓
DES PERMISSIONS
    ↓
UN OU PLUSIEURS PÉRIMÈTRES
    ↓
DES DONNÉES AUTORISÉES
    ↓
DES ACTIONS AUTORISÉES
    ↓
UNE TRAÇABILITÉ COMPLÈTE

Toute décision d’architecture doit privilégier :

sécurité + maintenabilité + évolutivité + traçabilité + compatibilité avec l’existant + protection des données.

Commence impérativement par l’audit du dépôt réel et ne modifie aucun fichier avant d’avoir établi l’état des lieux.

Recommandation pour Arena Agent Mode

Pour ton projet actuel, je ne lancerais pas ce prompt directement en mode Act sur toute l’application. Il est suffisamment important pour le découper en U0 → architecture IAM → backend → frontend → intégration → E2E.

Le point le plus important est que ce module devienne le socle d’autorisation commun aux modules déjà présents — Scolarité, Candidatures, Admissions, Inscriptions, Étudiants, Enseignants, Cours, Présences, Jurys, Graduation, Finances, Stages, RH, Patrimoine, etc. — plutôt que de créer un nouveau système d’utilisateurs isolé.

Si tu veux, je peux aussi te générer la version “Arena Agent Mode / Cline”, beaucoup plus opérationnelle, découpée en 10 prompts successifs P01 → P10, avec pour chaque prompt : objectif, fichiers à inspecter, modifications autorisées, tests obligatoires, critères de validation et commit checkpoint.
