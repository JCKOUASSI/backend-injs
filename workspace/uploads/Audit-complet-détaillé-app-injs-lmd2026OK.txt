0. SYNTHÈSE EXÉCUTIVE
================================================================================
L'application est une plateforme de gestion globale pour l'INJS Marcory, issue
d'un produit préexistant de gestion des présences par QR Code (« QR Badge /
SYGEP-CPFAE » du MEMFPMA) et en voie d'extension vers un Système d'Information
universitaire LMD complet (admissions/concours, scolarité, pédagogie, jurys,
diplômes, finances étudiantes, stages, administration, RH, patrimoine, EDT,
statistiques).
JUGEMENT D'ENSEMBLE : PRODUIT MATURE SUR LE CŒUR, EN MUTATION INACHEVÉE SUR LE PÉRIMÈTRE LMD.
Le « cœur historique » (formations, participants, formateurs, modules, séances,
pointage QR, exports, statistiques) est très complet, éprouvé, bien testé et
déployable. La couche LMD récemment ajoutée est, côté backend, remarquablement
avancée et disciplinée (modèles, workflows d'états, permissions dédiées, tests),
mais l'interface web n'accompagne pas encore toute cette richesse : quatre
domaines entiers ont une API testée sans aucun écran, et plusieurs modules ne
sont que partiellement intégrés.
FORCES (9 points)
  1. Socle backend solide : Django 5.1.4 + DRF, 20 applications métier,
     133 modèles, ~88 000 lignes de Python hors migrations.
  2. Très bonne couverture de tests backend : 943 méthodes de test (13 016
     lignes), CI exécutant migrations + suite complète + build Docker.
  3. Architecture de permissions mature et rôles métier fins (12 rôles,
     classes de permission par domaine, synchronisation Groupes Django).
  4. Chaîne LMD backend très avancée : admissions/concours, inscriptions
     administratives et pédagogiques, maquettes versionnées UE/ECUE,
     jurys, diplômes, équivalences, finances étudiantes, stages.
  5. Sécurité intégrée dès la conception : JWT + refresh, throttling login/
     scan, liaison d'appareils (DeviceBinding), piste d'audit, média non
     servis publiquement, durcissement HSTS en production, variables
     d'environnement, middlewares de démo strictement gardés par DEBUG.
  6. Fonctionnement multi-transports robuste (navigateur, iframe, mobile,
     PWA) avec API documentée (drf-spectacular / Swagger).
  7. Identité visuelle INJS posée : bleu nuit, bleu clair, effet de verre
     (glassmorphism), logo INJS — à conserver en refonte.
  8. Moteur d'exports PDF/Excel réutilisable (reportlab/openpyxl, 39 fichiers
     concernés) et travail préparatoire d'import Excel.
  9. État d'esprit « préserver l'existant » formalisé (règles workspace,
     migrations nombreuses mais cohérentes, pas de suppression de modules).
FAIBLESSES / RISQUES MAJEURS (synthèse — détail §13-14)
  R1. ÉCART BACKEND / FRONTEND (criticité HAUTE) : 4 domaines ~100 % backend
      (Stages, Patrimoine, Ressources Humaines, Administrations/courriers)
      n'ont AUCUN écran web ; les finances étudiantes ne sont exploitées
      qu'à 25 % dans l'UI ; les concours sont partiellement écrantés.
  R2. ABSENCE TOTALE DE TESTS FRONTEND (0 test) alors que l'UI est la couche
      qui porte les workflows LMD les plus sensibles ; 89 avertissements
      ESLint dont plusieurs dépendances d'effets React.
  R3. DOUBLES REPRÉSENTATIONS DE DONNÉES non résolues (groupes, catégorisation
      des participants, notes/ECUE, deux finances, formations sans lien vers
      le référentiel) — documentées mais non migrées ; risque de chiffres
      contradictoires entre modules.
  R4. GIGANTISME DE CERTAINS FICHIERS (jusqu'à 5 508 lignes côté UI, 4 980
      côté API) qui fragilise la maintenance et la revue de code.
  R5. HYGIÈNE DU DÉPÔT perfectible : jeux de données Excel/CSV/.numbers et
     staticfiles/ collectés versionnés dans Git ; README racine et résumés
      affichant encore l'ancienne identité « sygepcpfae / MEMFPMA » ;
     vestiges de service worker « qr-badge-v3 » et CDN tiers.
  R6. CI Mobile instable pour des raisons d'outillage : le lockfile était
      désynchronisé (corrigé pendant l'audit : meta 1.17.0 / test_api
      0.7.10) ; il reste un échec `flutter analyze` dû à un asset
      `assets/app.env` volontairement ignoré par Git (à traiter hors
      correctif lockfile).
  R7. Observabilité quasi absente : pas de Sentry/APM, 288 `print()` de
      débogage dans le code d'exécution, journalisation applicative à
      renforcer ; aucun test sur les domaines EDT, exports et dashboard.
  R8. Maquettes LMD ACTIVES modifiables sans verrou et notes sans piste
      d'audit immuable (risque pédagogique/juridique connu, prérequis aux
      jurys de délibération).
RECOMMANDATION GLOBALE
La refonte doit être une REFONTE D'ALIGNEMENT et non une réécriture : garder
le socle backend éprouvé et l'identité visuelle, compléter les chaînes de
valeur manquantes (UI des domaines orphelins, résorption des doubles
représentations, verrous pédagogiques), industrialiser la qualité (tests
frontend, observabilité, hygiène du dépôt) et unifier l'identité INJS-LMD.

2. ARCHITECTURE GLOBALE
================================================================================
Schéma logique :
                         ┌──────────────────────────────┐
                         │   Navigateurs web internes    │
                         │ React/Vite (rôles admin,      │
                         │ scolarité, finance, direction)│
                         └──────────────┬───────────────┘
                                        │ HTTPS, JWT (Authorization
                                        │ Bearer + X-JWT-Access)
  ┌──────────────┐        ┌─────────────▼──────────────┐      ┌─────────────┐
  │ App Flutter  │ HTTPS  │   BACKEND DJANGO / DRF      │ SQL  │ PostgreSQL  │
  │ iOS/Android  ├───────►│   port 8000 (Gunicorn prod) ├─────►│ (prod) /    │
  │ + PWA        │  JWT   │   Nginx en amont            │      │ SQLite démo │
  └──────────────┘        │                             │      └─────────────┘
                          │ - 20 apps métier (API+admin)│      ┌─────────────┐
  ┌──────────────┐        │ - exports PDF/Excel         │◄────►│ Redis cache │
  │ Admin Django │        │ - service worker / SPA      │      └─────────────┘
  └──────────────┘        └────────────────────────────┘
        │ /admin/
   (superusers / démo auto-login gardée par DEBUG)
Points d'architecture notables :
  - API unique sous /api/ (30 inclusions d'URLs racines), documentation
    OpenAPI/Swagger via drf-spectacular (/api/docs/, /api/schema/).
  - Authentification JWT (djangorestframework-simplejwt 5.4.0) avec transport
    flexible : en-tête Authorization, en-tête X-JWT-Access, paramètre
    ?access_token=, cookie HttpOnly SameSite=None; Secure (rafraîchissement
    multi-navigateurs/iframes), rafraîchissement par body ou localStorage en
    mode démo. Ces assouplissements sont INERTES hors DEBUG.
  - Le backend Django sert aussi le build React en SPA pour l'aperçu unique
    (PREVIEW_SPA) avec fallback de routes ; en production, Nginx/Gunicorn.
  - Découpage en apps Django métier cohérent avec les grands domaines
    fonctionnels ; certaines apps ont un fichier de vues monolithe
    (formations/api_views.py, presences/views.py, exports/views.py,
    statistiques/views.py), les apps LMD récentes utilisent plutôt des
    fonctions API explicites (api.py) et des workflows par transitions.

5. APPLICATION MOBILE FLUTTER + PWA
================================================================================
5.1 Périmètre
  Application destinée aux AUDITEURS (étudiants/stagiaires) et FORMATEURS :
  connexion, tableau de bord, scan QR de séances (mobile_scanner 7.x,
  sans Google ML Kit → compatible simulateurs arm64/iOS récents),
  historique des pointages, questionnaires d'évaluation, fiche profil,
  changement de mot de passe, télémétrie d'appareil (device_info_plus,
  geolocator, battery_plus), gestion des permissions
  (permission_handler), persistance sécurisée (flutter_secure_storage),
  keepalive en avant-plan (flutter_foreground_task), ouverture de liens
  (url_launcher), variables d'environnement (flutter_dotenv).
  - 40 fichiers Dart dans lib/, 7 818 lignes ; 3 fichiers de tests.
  - Thème dédié (lib/theme/qr_badge_theme.dart), widgets réutilisables
    (logo, cadre de scan, bannière de statut de session, cartes,
    empty-states), garde-fous de déconnexion, reprise de session,
    journalisation.
  - Permissions iOS décrites dans Info.plist (caméra, localisation,
    Bluetooth) ; politique de confidentialité mobile embarquée/ouvrable.
5.2 PWA
  - La compilation Flutter web est utilisée en PWA ; heartbeat en
    avant-plan non supporté hors onglet actif (documenté) ; les appareils
    Web sont préfixés FLUTTER_PWA_ et exclus des sanctions de heartbeat.
  - Un service worker historique (backend/static/sw.js, « qr-badge-v3 »)
    pré-cache encore des CDN Bootstrap/html5-qrcode : vestige de la page
    de badgeage HTML à faire évoluer/supprimer lors de la refonte.
5.3 CI / dépendances
  - CI : Flutter 3.41.7 stable, `flutter pub get --enforce-lockfile` puis
    `flutter analyze`.
  - CONSTAT TRAITÉ PENDANT L'AUDIT : le pubspec.lock avait été généré avec
    un Flutter de borne différente (borne flutter >=3.38.4) ; sous
    3.41.7, le SDK fige deux dépendances à des versions plus basses que
    celles verrouillées : meta 1.18.0 → 1.17.0 et test_api 0.7.11 →
    0.7.10, d'où « Unable to satisfy pubspec.yaml using pubspec.lock —
    Would change 2 dependencies — exit 65 ». Le lock a été régénéré sous
    Flutter 3.41.7 (via CI, aucune dépendance directe modifiée) :
    `--enforce-lockfile` retourne maintenant EXIT 0 et le lock n'est plus
    modifié par un `pub get` simple.
  - RESTE À TRAITER (hors sujet lockfile) : `flutter analyze` échoue sur
    UN avertissement considéré bloquant : l'asset déclaré
    `assets/app.env` n'existe pas car il est volontairement ignoré
    (.gitignore). Solutions recommandées : versionner un fichier
    `assets/app.env.example` et le déclarer, ou générer un app.env vide
    en étape CI, ou transformer l'avertissement en configuration non
    bloquante tout en conservant le chargement défensif déjà en place
    (lib/main.dart tolère l'absence du fichier).
  - 70 paquets ont des versions plus récentes incompatibles avec les
    contraintes actuelles (ex. mobile_scanner 7.2 vs 7.4, geolocator
    13.0.4 vs 14, permission_handler 11 vs 13) : mise à jour mineure à
    planifier, sans urgence.

    variables d'environnement, restreints à /admin/ ou au seul mode

  docs/CARTOGRAPHIE_CIBLE_INJS_LMD.md ; la refonte doit fournir le plan
