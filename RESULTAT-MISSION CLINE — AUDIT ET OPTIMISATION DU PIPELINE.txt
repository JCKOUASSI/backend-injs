================================================
RÉSULTAT
================================================
Audit et optimisation ciblée du pipeline GitHub Actions CI de backend-injs réalisés localement, sans modification métier, sans suppression de contrôle et sans push GitHub.

CAUSE PRINCIPALE
Le goulot principal est le démarrage de PostgreSQL via Docker sur le runner self-hosted. Les commandes Docker de suppression, de création et de vérification de disponibilité n'étaient pas bornées. Un run GitHub CI a échoué sur cette étape après le timeout de 30 secondes ajouté dans le diagnostic ; un run antérieur a laissé le job Backend à environ 3 h 28 et le pipeline total à environ 8 h 54, avec les jobs mis en file sur un runner unique. Le daemon Docker local est actuellement non responsive : `docker version` et `docker ps` dépassent 8 secondes lors d'un probe borné.

Le runner `backend-injs-runner` est actuellement `offline` et `busy=true`, avec les labels `self-hosted, macOS, ARM64, backend-injs`. Un seul runner ne peut pas exploiter tout le parallélisme théorique des quatre jobs et crée une concurrence sur le daemon Docker partagé.

CAUSES SECONDAIRES
- Absence de cache pip dans le workflow Backend.
- Recréation de l'environnement Python à chaque exécution et upgrade pip inutile.
- Absence de copie de `.env.example` vers `assets/app.env` avant Flutter.
- Les quatre jobs sont indépendants, sans `needs`, mais l'infrastructure observable ne permet pas de garantir leur simultanéité.
- Les tests Django n'ont pas été profilés localement avec une base PostgreSQL fonctionnelle ; aucune conclusion artificielle sur les 10 tests les plus lents n'est faite.

OPTIMISATIONS APPLIQUÉES
1. Timeout Backend de 90 minutes, au-dessus du run réussi observé d'environ 58 minutes mais inférieur aux blocages de plusieurs heures.
2. Timeouts de 20 minutes pour Frontend, Vitest et Mobile.
3. Ciblage explicite du runner par `runs-on: [self-hosted, macOS, ARM64, backend-injs]`.
4. Checkout effectué avant le démarrage PostgreSQL.
5. Cache pip `actions/cache@v4` basé sur `backend/requirements.txt`, sans cache de base ni secret.
6. Environnement Python réutilisé avec `venv --clear` et suppression de l'upgrade pip inutile.
7. Commandes Docker PostgreSQL bornées : 30 s suppression, 60 s création, 10 s vérification ; erreurs et timeouts visibles.
8. Nettoyage PostgreSQL `if: always()` borné à 30 secondes.
9. Copie CI de `.env.example` vers `assets/app.env` avant Flutter.
10. Conservation intégrale des contrôles Django, API, CURP/U0, U1/U2, audit P01-01, smoke, Docker/collectstatic, Vite, Vitest, Flutter et artefacts.

Aucune optimisation à risque n'a été appliquée : pas de `--parallel`, pas de `--keepdb`, pas de suppression de migration ou de test, pas de `skip`, pas de `|| true` pour masquer un test et pas de modification d'assertion.

RISQUES / POINTS À SURVEILLER
- Le runner est actuellement offline ; il faut le rétablir avant toute mesure CI réelle.
- Le partage Docker entre jobs reste un facteur de contention ; plusieurs runners dédiés ou un runner Backend isolé permettraient un parallélisme réel.
- Réévaluer le timeout Backend après le premier run réussi avec daemon restauré.
- Le cache pip sera validé par le premier run ; sa clé dépend de `backend/requirements.txt`.
- `--parallel` et `--keepdb` restent désactivés jusqu'à analyse des fixtures et tests PostgreSQL.
- Aucun push n'avait été effectué avant validation humaine ; le push final a été réalisé normalement sur `origin/main`, sans force. Aucune modification du VPS, aucune opération destructive et aucune modification de données n'ont été effectuées.
