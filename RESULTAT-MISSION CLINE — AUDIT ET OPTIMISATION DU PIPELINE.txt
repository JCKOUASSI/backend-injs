RÉSULTAT
================================================
CAUSE PRINCIPALE
Le goulot n'est pas la logique métier Django : sur le run CI GitHub 35930932967 (SHA 75a9cb10), l'étape « Démarrer PostgreSQL CI » a consommé 255,6 minutes avant annulation. Le job Backend n'a pas atteint Python, les tests, les smoke tests, le contrat API ni la vérification Docker. La commande `docker rm -f` puis `docker run` n'était pas bornée sur le runner self-hosted `backend-injs-runner` (macOS ARM64, un seul runner partagé par les quatre jobs).

CAUSES SECONDAIRES
- Les quatre jobs utilisent le même runner et ne peuvent donc pas réellement s'exécuter en parallèle sur l'infrastructure actuelle.
- Le job Backend exécutait la migration, 2 041 tests Django, les contrôles CURP/U0/U1/U2, l'audit P01-01, le contrat API, les smoke tests et la construction/validation Docker dans un seul job.
- La suite Django utilise des `TransactionTestCase`, des tests de migration, des tests de cache et des fixtures/ressources temporaires ; `--parallel` n'a pas été activé sans validation PostgreSQL complète, afin d'éviter une contamination des tests.
- Le cache pip Python manquait et le virtualenv Python CI était recréé à chaque run.
- Les avertissements drf-spectacular et ESLint observés sont préexistants et ne sont pas des contrôles supprimés ou masqués.

OPTIMISATIONS APPLIQUÉES
1. Ajout de `timeout-minutes: 90` au job Backend, basé sur le run réussi à 58,1 minutes, avec une marge de sécurité ; ajout de 20 minutes aux jobs Frontend, Vitest et Mobile.
2. Remplacement du `docker rm -f`/`docker run` non bornés par un script Python embarqué avec limites de 30 s pour le nettoyage, 60 s pour le démarrage, 10 s pour chaque `pg_isready`, et journalisation limitée à 100 lignes en cas d'échec.
3. Ajout d'un nettoyage PostgreSQL `if: always()` et borné à 30 s, sans `|| true` masquant les contrôles fonctionnels.
4. Checkout puis `actions/setup-python@v5` avec Python 3.12 et cache pip basé sur `backend/requirements.txt` avant le bootstrap Docker PostgreSQL ; cela garantit l'interpréteur Python utilisé par le workflow et évite de démarrer le conteneur si la préparation Python échoue.
5. Conservation de `python -m venv --clear .venv-ci` et de l'installation des dépendances ; aucune dépendance n'est figée ou inventée.
6. Conservation intégrale des contrôles Backend : tests Django, `check_repo_hygiene`, `collectstatic`, contrat drf-spectacular P00-08, smoke INJS-LMD, smoke CURP U0, U1, U2, audit P01-01 et image Docker/permissions/collectstatic.
7. Aucun `needs` supprimé ou ajouté : Backend, Frontend, Vitest et Mobile restent des jobs indépendants. Ils restent sérialisés en pratique par l'unique runner self-hosted actuel. Plusieurs runners donneraient un gain de parallélisme, sans création automatique de runner.
