--------------------------------------------------------------------------------
2. ANALYSE — POINTS RELEVÉS
--------------------------------------------------------------------------------
A. Comportement normal à ne PAS interpréter comme une panne
   - <div id="root"></div> est vide dans le code source : React génère le DOM
     côté client (JavaScript). « Afficher le code source » montre toujours la
     coquille vide, même quand l'application fonctionne. Ce n'est pas une erreur.
   - La balise <script type="module"> est différée par défaut : le code s'exécute
     après lecture du HTML.

B. DÉFAUT CORRIGÉ N°1 (bloquant selon le réseau) — ressource externe render-blocking
   - index.html chargeait la feuille d'icônes depuis un CDN tiers :
       https://cdn.jsdelivr.net/npm/bootstrap-icons@1.11.3/font/bootstrap-icons.min.css
   - Une feuille de styles <link rel="stylesheet"> EST « render-blocking » : le
     navigateur retient l'affichage tant qu'elle n'est pas traitée.
   - Test réseau depuis l'environnement : ce CDN est INJOIGNABLE
       (curl -> code HTTP 000, ~0,03 s). Dans l'aperçu (passerelle proxy,
        réseau parfois restreint), cela provoque un blocage/retard d'affichage
        ou une page blanche/figée sur « chargement », et en tout état de cause
        la perte de TOUTES les icônes de l'interface.

C. DÉFAUT CORRIGÉ N°2 — aucune information en cas d'échec du chargement JavaScript
   - Si le bundle ne se charge pas (coupure réseau / proxy / cache périmé après
     une reconstruction, les noms de fichiers étant hashés), l'utilisateur reste
     sur une page blanche sans explication et sans action possible.

D. DÉFAUT CORRIGÉ N°3 (séances / connexion) — architecture proxy fragile en aperçu
   - Le port 3000 était desservi par un petit proxy Node maison qui recopiait
     des en-têtes « hop-by-hop » (Connection: keep-alive, Keep-Alive) et laissait
     passer X-Frame-Options: DENY. Derrière la passerelle HTTPS/HTTP2 de l'aperçu,
     la RÉPONSE du POST de connexion pouvait ne pas être correctement transmise au
     navigateur : le serveur journalisait bien « POST /api/auth/login/ 200 » mais
     le jeton n'était pas exploité côté client => appels suivants en 401 =>
     renvoi permanent à la page de connexion.
   - Réglage CSRF inopérant : une variable « CSRF_..._REGEXES » avait été ajoutée
     ; or Django ne comprend que CORS_..._REGEXES, pas d'équivalent regex pour CSRF.

E. Architecture cible retenue
   - Un seul serveur / une seule origine : Django sert DIRECTEMENT le build React
     (application + API + admin). Plus de proxy Node, plus de cookie cross-site,
     plus de CORS/CSRF inter-origines ni de WebSocket pour afficher la page.

7. RECOMMANDATIONS
--------------------------------------------------------------------------------
- Conserver la règle « aucune ressource tierce bloquante » (icônes/polices
  embarquées localement) ; si un CDN est un jour voulu en production, l'ajouter
  en <link rel="preload" ... onload> ou en import géré par le bundler, jamais en
  stylesheet bloquant sans solution de repli.
- En production réelle, servir le build via la configuration Nginx/Docker déjà
  présente ; ne PAS activer DEBUG/PREVIEW_SPA/dev_middleware (qui sont réservés à
  la démo locale).
- Le bundle principal dépasse 500 Ko : un découpage par routes (React.lazy, déjà
  partiellement utilisé) réduirait le temps de premier affichage.

8. DIAGNOSTIC COMPLÉMENTAIRE (après analyse des journaux d'une vraie tentative)
================================================================================
Les journaux du serveur sur une tentative réelle du navigateur dans l'aperçu
(IP passerelle 10.12.0.138) montraient :
  POST /api/auth/login/ ........................ 200  (identifiants corrects)
  GET  /api/formations/list|stats/secretariats  401  (jeton NON reçu)
  GET  /api/statistiques/rapports/notifications  401
  POST /api/auth/token/refresh/ ............... 400  (cookie NON renvoyé)
=> En ligne de commande / tests internes (même origine) tout fonctionnait :
   le problème est lié au CONTEXTE IFRAME CROSS-SITE de l'aperçu :
   (a) les cookies SameSite=Lax ne sont pas transmis dans une iframe tierce ;
   (b) l'en-tête Authorization peut être filtré par certaines passerelles.

NOUVELLES TÂCHES (correctif « transport d'authentification robuste »)
--------------------------------------------------------------------------------
[T8] Authentification JWT multi-transports — backend/authentication/auth_classes.py
     Nouvelle classe FlexibleJWTAuthentication (remplace JWTAuthentication dans
     config/settings.py) qui accepte le jeton d'accès dans cet ordre :
       1) Authorization: Bearer <jeton>                 (standard, prod)
       2) X-JWT-Access: <jeton>                         (secours si passerelle)
       3) ?access_token=<jeton>                         (URL directe/exports)
     La production n'utilise que le chemin 1 ; les autres ne sont alimentés
     que par le build d'aperçu.

[T9] Cookies compatibles iframe cross-site
     - authentication/views.py : attributs du cookie de refresh pilotés par
       variables d'env JWT_COOKIE_SAMESITE / JWT_COOKIE_SECURE ; en aperçu
       SameSite=None; Secure (obligatoire pour être envoyé en iframe tierce).
     - config/settings.py : idem pour les cookies de SESSION et CSRF de l'admin
       Django via COOKIE_SAMESITE=None (CSRF_COOKIE_*/SESSION_COOKIE_*).
       => corrige le 403 « CSRF cookie not set » à la connexion admin dans l'iframe.

[T10] Frontend : transport de secours + refresh sans dépendre des cookies
     - src/services/api.js : chaque requête authentifiée envoie désormais
       Authorization: Bearer **et** X-JWT-Access (double en-tête).
     - src/context/AuthContext.jsx : quand VITE_REFRESH_FALLBACK=1 (build
       d'aperçu), le refresh token est aussi conservé en stockage local ; le
       rafraîchissement fonctionne alors par le CORPS de la requête même si les
       cookies tiers sont totalement bloqués (ex. Safari). En production, sans
       ce fanion, seul le cookie HttpOnly est utilisé (risque R6 inchangé).
     - frontend/.env : VITE_REFRESH_FALLBACK=1 pour l'aperçu.

[T11] Journalisation de diagnostic temporaire — config/dev_debug_middleware.py
     (DEBUG uniquement) : trace pour /api/ la présence de Authorization, du
     cookie refresh, Origin et Sec-Fetch-*. À RETIRER après validation.

9. CORRECTION FINALE DE LA CONNEXION ADMIN (port 8000/3000) — 403 CSRF en iframe
================================================================================
CONSTAT
  Même avec des cookies SameSite=None; Secure, l'admin Django renvoyait
  « 403 Interdit — La vérification CSRF a échoué ». L'iframe de prévisualisation
  n'enregistre/ne renvoie en fait AUCUN cookie tiers (sandbox sans
  allow-same-origin ou blocage total des cookies tiers par le navigateur).
  L'app React, sans dépendance aux cookies, fonctionnait ; pas l'admin qui
  exige obligatoirement deux cookies (CSRF + session).

[T12] Admin de démonstration sans cookie — backend/config/demo_admin_middleware.py
     Nouveau middleware DemoAdminAutoLoginMiddleware, branché AVANT
     CsrfViewMiddleware, STRICTEMENT réservé à la démo locale :
       * double garde-fou : ne s'active QUE si DEBUG=True ET
         DEMO_ADMIN_AUTOLOGIN=1 (totalement inerte en production) ;
       * ne s'applique QU'aux chemins /admin/ ;
       * 1) dispense ces vues de la vérification CSRF par cookie
         (attribut csrf_processing_done positionné avant CsrfViewMiddleware) ;
       * 2) authentifie automatiquement le superutilisateur de démo à chaque
         requête (aucun cookie de session nécessaire).
     L'API DRF hors /admin/ reste protégée : /api/formations/list sans jeton
     renvoie bien 401. Le mode de production (DEBUG=False) ignore ce middleware.

[T13] Variables d'environnement d'aperçu ajoutées (backend/.env + start_dev.sh)
       JWT_COOKIE_SAMESITE=None / JWT_COOKIE_SECURE=1   (refresh JWT)
       COOKIE_SAMESITE=None                              (session + CSRF Django)
       DEMO_ADMIN_AUTOLOGIN=1                            (admin démo sans cookie)
     Côté frontend : VITE_REFRESH_FALLBACK=1 dans frontend/.env.

VÉRIFICATIONS FINALES (ports 8000 ET 3000, sans aucun cookie, aucun jeton CSRF)
  GET  /admin/                         -> 200 (tableau de bord admin directement)
  GET  /admin/login/?next=/admin/      -> 302 vers /admin/ (déjà authentifié)
  POST /admin/login/ (sans CSRF)       -> 302 Location: /admin/  (faisait 403)
  GET  /admin/authentication/user/    -> 200 (section utilisateurs)
  GET  /admin/auth/                    -> 200
  POST /admin/logout/                  -> 302 puis GET /admin/ -> 200 (ré-auto)
  GET  /api/formations/list sans jeton -> 401 (l'API RESTE bien protégée)
  Application React (port 3000)        -> connexion + tableau de bord OK

SYNTHÈSE SÉCURITÉ
  - En production (DEBUG=False, variables d'aperçu absentes) : aucun de ces
    assouplissements n'est actif ; CSRF, session et cookie HttpOnly fonctionnent
    comme prévu par le code d'origine.
  - Les changements T12/T13 ne concernent que la démonstration locale
    sandbox/SQLite de l'aperçu.
